### **Aljabr Roadmap (v0.4.0): Prose Foundations**

**Strategic Vision**

The original motivation for aljabr was a text editor. v0.3.x built the foundations — algebraic data types, reactive primitives, a renderer abstraction with two production hosts (DOM and Canvas) — but the editor itself remained downstream of libraries that weren't quite right. The contenteditable surface in modern browsers is a chaotic event soup: input events fragment across `inputType` codes, composition events interleave with regular input during IME, paste lands raw HTML in the DOM before authors can intercept, and selection is owned by the browser's `Range` API which speaks DOM nodes and offsets — useless at the document-model level.

Existing solutions (ProseMirror, Lexical, Slate) all build *on top of* the DOM event soup and pay a recurring tax in hacking around it. v0.4.0 takes the opposite stance: **the renderer owns the DOM under contenteditable; the browser never writes to it.** Every browser intent flows through `beforeinput` (or composition handlers, or the paste interceptor), gets converted to a typed command, validates through a protocol that may reject it, and only then mutates the document model. The DOM is rewritten from the model — never read back to recover state.

The author-facing surface is a single `<Prose>` Component imported from `aljabr/ui/prose`. The author owns the editor state as a `Dispatcher` (canonical variable name: `editor`), passes it to `<Prose state={editor}>`, and the Component encapsulates everything else — its own `ProseRenderer`, the contenteditable DOM, the `beforeinput` translator, and a custom diff cycle from `editor.state().doc` to the DOM. The Component pattern makes prose interop with arbitrary parent renderers — drop `<Prose>` into a `DomRenderer` mount tree next to toolbars and chrome. A symmetric `<Canvas>` Component ships at the same time.

This release also reshapes the renderer abstraction itself. `Renderer.create(host)` is the central primitive every concrete renderer (Dom, Canvas, Prose) is built on. Hosts are stateless vtables that grow one new method — `attach(container)` — to bridge from a parent-renderer-supplied container to the host's internal root, optional protocol, and disposer. Surface binding moves to `mount`: `r.mount(fn, container)` is uniform across renderers. The previous `createCanvasRenderer(canvas).mount(fn)` pre-currying is retired; every renderer's mount takes a container. Hosts are renamed to capitalized form (`DomHost`, `CanvasHost`, `ProseHost`).

Phase 0 lands the architectural rebuild and the `<Canvas>` Component. Phases 1 and 3 (already implemented on the v0.4.0 branch) get small additive revisions — chiefly the Embed extension point and first-class Lists in the document model, plus list-operation commands. Phases 4–7 build the prose editor on the new foundations: `<Prose>` Component, `ProseHost` (a superset of `DomHost`), `ProseRenderer.create()`, native selection, synthetic events, and `parse.jsx` (registry-aware). IME, paste, history, and keyboard bindings ship in v0.4.1; collaborative cursors, editable structured embeds, and tables are deferred to v0.4.x / v0.5.0.

The package lives at `aljabr/ui/prose` — a sibling of `aljabr/ui/dom` and `aljabr/ui/canvas`. It ships its own JSX runtime at `aljabr/ui/prose/jsx-runtime` for parse.jsx static authoring; authors extend the runtime's intrinsic set with their registered embed tags via TypeScript module augmentation.

### Phase 0: Renderer Architecture Rebuild

The architectural prerequisite for the rest of v0.4.0. Reshapes `aljabr/ui` so every concrete renderer is a thin wrapper over `Renderer.create(host)` with a stateless host that owns surface adoption.

#### 0.1 — `Renderer.create` central abstraction

`createRenderer` is renamed to `Renderer.create`. Same signature: `Renderer.create(host)` returns `{ view, mount }`; `mount(fn, container)` returns an unmount function. The optional `RendererProtocol` arg is removed from `Renderer.create` — protocols now come from the host's `attach()` (see §0.3).

#### 0.2 — Stateless hosts, capitalized

Existing host singletons are renamed:

- `domHost` → `DomHost`
- `canvasHost` → `CanvasHost`

Hosts remain stateless vtables. State for a specific mounted surface lives in closures returned from `attach()`.

A new host is introduced:

- `ProseHost` — a strict superset of `DomHost`. Handles all DOM tags identically to `DomHost`, plus prose-specific behavior (mark wrapping, void-node rendering, embed projection) when the inner JSX names prose intrinsics. Used by `ProseRenderer`.

#### 0.3 — `RendererHost.attach(container)`

The `RendererHost` interface gains one method:

```ts
interface RendererHost<N, E extends N, Container = E> {
    // existing: createElement, createText, insert, remove, setProperty,
    // setText, parentNode, nextSibling, onMount?, onUnmount?, onUpdate?
    attach(container: Container): {
        root: E
        protocol?: RendererProtocol
        dispose: () => void
    }
}
```

`Container` defaults to `E` (the dom/prose case where the user-facing container *is* the host's element type) and is overridden where they differ — canvas: `Container = HTMLCanvasElement`.

`attach`'s job is to adapt the user-supplied container to (a) the host's internal root element, (b) an optional protocol the renderer should use, and (c) a disposer the renderer chains into mount cleanup.

- `DomHost.attach(el)` → `{ root: el, dispose: () => {} }` — identity.
- `CanvasHost.attach(canvas)` → builds a synthetic `<group>` root, installs the rAF protocol over the supplied canvas + 2d ctx, attaches pointer/wheel listeners; `dispose` removes listeners and clears the canvas.
- `ProseHost.attach(el)` → `{ root: el, dispose: detachBeforeInput }` — DOM-level prose lifecycle setup (the contenteditable attribute and `beforeinput` listener live in the `<Prose>` Component's `mounted` callback, not in `attach` — see §4.2).

The renderer reads the record after `attach` and chains `record.dispose()` into the `mount`-returned unmount.

#### 0.4 — Convenience renderer wrappers

Each concrete renderer ships a thin static-method wrapper:

```ts
DomRenderer.create()    // ≡ Renderer.create(DomHost)
CanvasRenderer.create() // ≡ Renderer.create(CanvasHost)
ProseRenderer.create()  // ≡ Renderer.create(ProseHost)
```

Each wrapper returns `{ view, mount }` — the same shape `Renderer.create` returns. Authors can use either the wrapper or `Renderer.create(host)` directly; they're isomorphic.

The legacy `createRenderer` and `createCanvasRenderer` exports are removed.

#### 0.5 — `<Canvas>` Component

A new Component in `aljabr/ui/canvas` symmetric to v0.4.0's `<Prose>` (Phase 4). Authors import `Canvas` from `aljabr/ui/canvas` and use it inside any parent renderer:

```tsx
import { Canvas } from "aljabr/ui/canvas"
import { Scene } from "./scene"  // canvas-jsx file exporting () => ViewNode

/** @jsxImportSource aljabr/ui/dom */
<div>
    <Toolbar />
    <Canvas viewport={vp}>{Scene}</Canvas>
</div>
```

Implementation: `<Canvas>` returns a `<canvas>` view node with a `mounted` callback that creates `CanvasRenderer.create()`, mounts the children function, and defers cleanup via the `mounted` Scope. The raw `<canvas mounted={...}>` escape hatch remains for authors who need a ref to feed external libraries (Three.js, Pixi, etc.) — `<Canvas>` is the high-level path; raw `<canvas>` is the low-level path.

#### 0.6 — Migration scope

- Demos under `public/` are updated to the new shape (canvas demos move from `createCanvasRenderer(canvas).mount(fn)` to `CanvasRenderer.create().mount(fn, canvas)` or `<Canvas>`-Component-based composition).
- The style guide ([docs/guides/style-guide.md](../guides/style-guide.md)) gains a UI section describing the renderer abstraction, host contract, and Component-vs-host trade-offs (currently absent — flagged during Phase 4 grilling).

#### 0.7 — Acceptance criteria

- `Renderer.create(host)` exported from `aljabr/ui`. Legacy `createRenderer` export removed.
- `DomHost`, `CanvasHost` exported from their respective submodules with `attach()` implemented; `domHost` / `canvasHost` (lowercase) removed.
- `DomRenderer.create()`, `CanvasRenderer.create()` exported as thin wrappers.
- `<Canvas>` Component exported from `aljabr/ui/canvas`.
- Existing renderer/canvas tests updated for the new shape; new tests for `attach()` semantics across hosts.
- Public demos type-check and run against the new shape.
- Style guide UI section landed.

### Phase 1: Document Model ✅ implemented (additive revisions land in Phase 0/4 work)

#### 1.1 — Primitive Set (Closed)

The renderer ships a closed primitive set. Authors compose with these via JSX in `parse.jsx` static authoring; at runtime, the renderer projects from `editor.state().doc` into this same primitive vocabulary internally. Custom semantic widgets (video players, polls, stickers, mention chips that aren't text) are *registered embeds* — schema-typed payloads with author-supplied render components — not new variants in the renderer.

```
Structural:  <document>, <break>
Block:       <block>, <heading level={1..6}>, <quote>, <code>, <list ordered>, <listItem>
Inline:      <text>
Void:        <hr>, <blockEmbed name payload>, <inlineEmbed name payload>
Default-registered embed: <image src alt caption>  → BlockEmbed("image", { src, alt, caption })
```

Notes on each:

- **`<document>`** is the root. Used by `parse.jsx` (static document authoring) only. Runtime projection emits children directly into the contenteditable surface owned by `<Prose>`; the Document variant is not represented as a separate JSX element at runtime.
- **`<break>`** is a hard break inside a block (Shift-Enter behaviour). Structural primitive; no payload.
- **`<block>`** is the default block — the "paragraph."
- **`<heading level>`** carries a `level` prop in `1..6`. Level is part of the payload, not the tag — there is one heading node, not six.
- **`<quote>`** is a blockquote container. Holds blocks (including nested quotes).
- **`<code>`** is a block-level code container. Carries an optional `language` prop. Inline code is the `code` mark on `<text>`.
- **`<list>`** is a list container. Carries an `ordered` boolean prop. Holds `<listItem>` children. Lists may nest (a `<listItem>` can contain a nested `<list>`).
- **`<listItem>`** is a list entry. Holds blocks (most commonly a single `<block>`).
- **`<text>`** is the only inline primitive. All inline formatting — bold, italic, link, color, mention, comment-thread anchor — is expressed via marks on `<text>`. See Phase 1.2.
- **`<hr>`** is a void horizontal rule. Structural primitive; no payload.
- **`<blockEmbed name payload>`** / **`<inlineEmbed name payload>`** — opaque void nodes that delegate rendering to a registered author component. The `name` keys into the embed registry (passed to `<Prose embeds={…}>`); `payload` is `Schema`-validated against the registered shape. See Phase 4 §4.5.

**Default embed registrations** ship with the package: `image` (block-level — `BlockEmbed("image", { src, alt, caption })`). Authors override or remove via the `embeds` prop on `<Prose>`. The reason `image` is an embed rather than a structural primitive: it has author-controllable payload and rendering, which is exactly the embed pattern. `<hr>` and `<break>` stay structural because they have no payload and no author-controllable rendering — they're editor primitives, not author content.

**Why a closed structural set + open embed extension:** structural primitives (block flow, list nesting, headings, quotes, code blocks) carry editor semantics — selection traversal, command behavior, validation rules — that the renderer must understand intimately. Opening these to author registration adds ceremony (NodeSpec interfaces, validation hooks) for the wrong axis. Author-defined *content* (videos, charts, mentions-as-widgets, custom interactive embeds) doesn't need editor semantics: it's atomic from the editor's perspective (selected as a unit, deleted as a unit, no internal traversal in v0.4.0). The Embed extension point captures exactly this case — schema-typed payload, registered renderer, void lifecycle. The split aligns extension surface to the actual extension axis authors need.

**Mentions, comment anchors, custom inline annotations** are *marks*, not embeds. A mention is text content (`@alice`) with metadata; selection traverses it character-by-character; backspace deletes one character at a time. Phase 1.2's marks system covers this — `MarkSet.merge({ Mention: (userId) => ({ userId }) })` is the entire extension. Embeds are reserved for the void/atomic case where the content has no internal text the editor traverses.

**Editable structured embeds** (callout cards with editable title + body, code-playground cards with editable code) are deferred to v0.4.x — see Phase 8. v0.4.0 ships only void embeds.

#### 1.2 — Marks Model

Inline formatting is **marks**, applied as props on `<text>`. Three categories:

- **Style marks (boolean):** `bold`, `italic`, `underline`, `strike`, `code`. Each is a boolean prop.
- **Payload marks (object):** `link={{ href }}`, `color`, `backgroundColor`, `fontFamily`, `fontSize`. Each is a typed prop carrying its data inline.
- **Custom marks (typed union):** `marks={[MarkSet.Mention({ userId: "..." }), MarkSet.Comment({ threadId: "..." })]}`. The `marks` prop accepts an array of `MarkSet` variants — one per author-defined mark on this `<text>` node. `MarkSet` is a union built with the same machinery as `ProseCommand`, so authors extend it via `MarkSet.merge({ Mention: (userId: string) => ({ userId }) })` and the schema layer serializes via `Schema.variant(MarkSet, {...})`.

Examples:

```tsx
<text bold>plain bold</text>
<text bold italic code>multiple style marks</text>
<text link={{ href: "https://..." }}>clickable</text>
<text color="#f00" backgroundColor="#ff0">highlighted</text>
<text bold marks={[MarkSet.Mention({ userId: "123" })]}>@jamel</text>
```

**Why a typed union and not a record:** custom marks need to be serializable through `aljabr/schema` for the internal-clipboard format and (eventually) collaborative-editing transports. A record-shaped `marks={{ mention: { userId } }}` prop has no place to declare per-key payload schemas; a `MarkSet` union does (it composes with `Schema.variant` directly). It also opens marks to `match()` exhaustiveness checking for authors who pattern over them in their own components. The cost is one extra wrapping (`MarkSet.Mention(payload)` instead of `{ mention: payload }`) — accepted as the price of typed extensibility.

**DOM mapping (default):**

- Style marks emit minimal HTML: `bold` → `<strong>`, `italic` → `<em>`, `underline` → CSS, `strike` → `<s>`, `code` → `<code>`.
- Payload marks emit attributes or wrapping elements: `link` → `<a href>`, `color` → inline `style="color:..."`, font marks → inline styles.
- Custom marks default to `data-*` attributes derived from their tag (`MarkSet.Mention({ userId: "123" })` → `data-mention-user-id="123"`).

Authors can override default rendering for custom marks by providing a per-variant `render` function — that's a v0.4.2 ergonomic; v0.4.0 ships only the default mapping.

#### 1.3 — Implementation Strategy

Document nodes are a recursive tagged union. Because TypeScript can't infer the recursive `ProseNode[]` field while inferring the union itself, we follow the same pattern `Validation` uses in the codebase: declare each variant's `Variant<>` type alias first, then build the union via `union(...).typed({...})` with explicit casts.

```ts
import { union, type Variant } from "aljabr"

export type Document    = Variant<"Document",    { children: ProseNode[] }>
export type Block       = Variant<"Block",       { children: ProseNode[] }>
export type Heading     = Variant<"Heading",     { level: 1 | 2 | 3 | 4 | 5 | 6; children: ProseNode[] }>
export type Quote       = Variant<"Quote",       { children: ProseNode[] }>
export type Code        = Variant<"Code",        { language: string | null; children: ProseNode[] }>
export type List        = Variant<"List",        { ordered: boolean; children: ListItem[] }>
export type ListItem    = Variant<"ListItem",    { children: ProseNode[] }>
export type Text        = Variant<"Text",        { content: string; marks: MarkSet[] }>
export type HardBreak   = Variant<"HardBreak",   {}>
export type Hr          = Variant<"Hr",          {}>
export type BlockEmbed  = Variant<"BlockEmbed",  { name: string; payload: unknown }>
export type InlineEmbed = Variant<"InlineEmbed", { name: string; payload: unknown }>

export type ProseNode =
    | Document | Block | Heading | Quote | Code | List | ListItem
    | Text | HardBreak | Hr | BlockEmbed | InlineEmbed

export const ProseNode = union([]).typed({
    Document:    (children: ProseNode[]) => ({ children }) as Document,
    Block:       (children: ProseNode[]) => ({ children }) as Block,
    Heading:     (level: 1 | 2 | 3 | 4 | 5 | 6, children: ProseNode[]) =>
        ({ level, children }) as Heading,
    Quote:       (children: ProseNode[]) => ({ children }) as Quote,
    Code:        (language: string | null, children: ProseNode[]) =>
        ({ language, children }) as Code,
    List:        (ordered: boolean, children: ListItem[]) =>
        ({ ordered, children }) as List,
    ListItem:    (children: ProseNode[]) => ({ children }) as ListItem,
    Text:        (content: string, marks: MarkSet[]) => ({ content, marks }) as Text,
    HardBreak:   () => ({}) as HardBreak,
    Hr:          () => ({}) as Hr,
    BlockEmbed:  (name: string, payload: unknown) => ({ name, payload }) as BlockEmbed,
    InlineEmbed: (name: string, payload: unknown) => ({ name, payload }) as InlineEmbed,
})
```

**Embed payloads.** `BlockEmbed.payload` and `InlineEmbed.payload` are typed `unknown` at the document model level because their shape depends on the registered embed. Validation happens at the registry boundary (parse.jsx and command dispatch consult `editor`'s registered `Schema.variant` — see Phase 4 §4.5). Authors who type their embed registry strongly get compile-time payload checking at the use site (via TypeScript module augmentation of `ProseEmbeds` — see Phase 4 §4.6).

**Removal of `Image`.** The pre-revision Phase 1 shipped an `Image` variant. It is removed from the union and replaced by a default registration: `Image` is an embed named `"image"` with payload `{ src: string; alt: string | null; caption: string | null }`. The default registration is included automatically by `<Prose>` unless the author overrides or removes it via the `embeds` prop. Migration: any code referencing `ProseNode.Image(...)` updates to `ProseNode.BlockEmbed("image", { src, alt, caption })`.

Each variant carries a stable node ID assigned at construction (or read from a JSX `id` prop if present). IDs are non-enumerable on the variant payload to avoid serialization noise; they are read via a `getNodeId(node)` helper.

#### 1.4 — Acceptance Criteria

- All twelve variants (Document, Block, Heading, Quote, Code, List, ListItem, Text, HardBreak, Hr, BlockEmbed, InlineEmbed) are exported from `aljabr/ui/prose`.
- The `Image` variant is removed; default `image` embed registration ships with `<Prose>`.
- JSX type definitions exist for each structural primitive, with prop types matching the union variant payloads. Embed JSX intrinsics (`<image>` initially; author embeds via module augmentation — see Phase 4) resolve to `BlockEmbed` / `InlineEmbed` nodes.
- The test file `test/ui/prose/document-model.test.ts` covers: variant construction across all twelve variants, node ID assignment and stability, custom-mark composition (`MarkSet.merge`), block-vs-inline placement constraints (including list nesting), `BlockEmbed`/`InlineEmbed` placement rules.
- Documentation in `docs/api/prose/document-model.md` describes each primitive, the marks model, the embed extension point, and the closed-structural-open-embed rationale.

### Phase 2: `EditorRange` and `RangePoint` ✅ shipped

#### 2.1 — Shape

`EditorRange` is a tagged union via `union()`. The discriminant is the framework `[tag]` symbol — there is no `kind` field on the payload.

```ts
import { union, type Variant } from "aljabr"

export type Cursor    = Variant<"Cursor", { point: RangePoint }>
export type TextRange = Variant<"Text",   { anchor: RangePoint; focus: RangePoint }>
export type NodeRange = Variant<"Node",   { nodeId: string }>
export type EditorRange = Cursor | TextRange | NodeRange

export const EditorRange = union([]).typed({
    Cursor: (point: RangePoint) => ({ point }) as Cursor,
    Text:   (anchor: RangePoint, focus: RangePoint) => ({ anchor, focus }) as TextRange,
    Node:   (nodeId: string) => ({ nodeId }) as NodeRange,
})
```

`RangePoint` is a payload type (not a union — there is only one shape):

```ts
type RangePoint = {
    nodeId: string    // stable ID of the containing node
    offset: number    // character offset within the node's text
    line: number      // logical line (newline-delimited, NOT visual after wrap)
    col: number       // logical column
    absolute: number  // absolute character offset in the document
}
```

**Why stable node IDs:** the alternative is a path (`[0, 2, 1]` from the document root) or a direct `ViewNode` reference. Paths invalidate on every structural mutation; direct references are too tightly coupled to renderer internals and break across re-renders. Stable IDs survive structural mutations, are serializable (foundation for collaborative editing in v0.5.0), and let authors stamp their own IDs via a JSX `id` prop for cases like permalink anchors.

**Why logical (not visual) line/col:** word-wrapped paragraphs would force the renderer to maintain layout information that's expensive to compute on every cursor move. Authors who need visual coordinates for a popup or tooltip (e.g., autocomplete dropdown anchored to the cursor) read the browser's `getBoundingClientRect()` on the active selection — that's already native behaviour and survives wrapping.

#### 2.2 — Three Modes Explained

- **`Cursor`** — collapsed selection; one `RangePoint`.
- **`Text`** — text selection; an `anchor` (where selection started) and `focus` (where selection ended). `focus` may precede `anchor` when the user drag-selects right-to-left.
- **`Node`** — node selection; a single void node (e.g., an `<image>` clicked once) is "selected" as a unit. Commands like `Delete` operate differently in this mode (remove the whole node) vs. text mode (remove the selected range).

#### 2.3 — Schema for Serialization

A prebuilt `editorRangeSchema` ships in `aljabr/ui/prose` for serializing/deserializing ranges (used by collaborative-editing transports in v0.5.0 and by the internal clipboard format in v0.4.1). Authors compose, override, or replace via the existing `aljabr/schema` builders.

The schema is built with `Schema.variant`, which handles `[tag]` (de)serialization. The default wire shape is the variant payload spread at the top level alongside a discriminant key — so `EditorRange.Cursor(point)` serializes as `{ type: "Cursor", point: {...} }`, *not* a nested `{ tag, payload }` envelope. Both the discriminant key (`"type"` by default) and per-variant tag remapping are configurable via `Schema.variant`'s `options` argument:

```ts
import { Schema } from "aljabr/schema"

export const editorRangeSchema = Schema.variant(EditorRange, {
    Cursor: Schema.object({ point: rangePointSchema }),
    Text:   Schema.object({ anchor: rangePointSchema, focus: rangePointSchema }),
    Node:   Schema.object({ nodeId: Schema.string() }),
})
```

Round-trip is provable via the free `roundtrip(schemaOrCodec, input)` utility from `aljabr/schema`.

#### 2.4 — Acceptance Criteria

- `EditorRange` and `RangePoint` are exported from `aljabr/ui/prose`.
- `editorRangeSchema` is exported and round-trips correctly via the `roundtrip` utility from `aljabr/schema`.
- A new test file `test/ui/prose/editor-range.test.ts` covers: variant construction, `match()` exhaustiveness over the three modes, schema round-trip, and the `RangePoint` invariants (`absolute` matches the sum of preceding nodes' content lengths).
- Documentation in `docs/api/prose/editor-range.md` describes the three modes, the stable-ID model, and the logical-coordinates choice.

### Phase 3: Built-in Command Union and Default `apply` ✅ shipped

#### 3.1 — The Built-in Command Union

Phase 3 ships **ten variants** (the planned eight plus `Compound` and a split-out `RemoveMark`). The recursive `Compound` payload forces the `Variant<>`-alias-then-`union` pattern; the `union([]).typed({...})` form (no traits) matches the rest of `aljabr/ui/prose`:

```ts
import { union, type Variant } from "aljabr"

export type SetCursorCmd      = Variant<"SetCursor",      { range: EditorRange }>
export type InsertCmd         = Variant<"Insert",         { content: string | ProseNode[]; at: RangePoint }>
export type DeleteBackwardCmd = Variant<"DeleteBackward", { range: EditorRange }>
export type DeleteForwardCmd  = Variant<"DeleteForward",  { range: EditorRange }>
export type FormatCmd         = Variant<"Format",         { mark: MarkSet; range: EditorRange }>
export type RemoveMarkCmd     = Variant<"RemoveMark",     { markTag: string; range: EditorRange }>
export type SplitBlockCmd     = Variant<"SplitBlock",     { at: RangePoint; newBlockId: string | null }>
export type MergeBlockCmd     = Variant<"MergeBlock",     { at: RangePoint }>
export type SetBlockKindCmd   = Variant<"SetBlockKind",   { range: EditorRange; kind: BlockKind }>
export type CompoundCmd       = Variant<"Compound",       { steps: ProseCommand[] }>

export type ProseCommand =
    | SetCursorCmd | InsertCmd | DeleteBackwardCmd | DeleteForwardCmd
    | FormatCmd | RemoveMarkCmd | SplitBlockCmd | MergeBlockCmd
    | SetBlockKindCmd | CompoundCmd

export const ProseCommand = union([]).typed({
    SetCursor:      (range: EditorRange) => ({ range }) as SetCursorCmd,
    Insert:         (content: string | ProseNode[], at: RangePoint) =>
        ({ content, at }) as InsertCmd,
    DeleteBackward: (range: EditorRange) => ({ range }) as DeleteBackwardCmd,
    DeleteForward:  (range: EditorRange) => ({ range }) as DeleteForwardCmd,
    Format:         (mark: MarkSet, range: EditorRange) =>
        ({ mark, range }) as FormatCmd,
    RemoveMark:     (markTag: string, range: EditorRange) =>
        ({ markTag, range }) as RemoveMarkCmd,
    SplitBlock:     (at: RangePoint, options?: { newBlockId?: string }) =>
        ({ at, newBlockId: options?.newBlockId ?? null }) as SplitBlockCmd,
    MergeBlock:     (at: RangePoint) => ({ at }) as MergeBlockCmd,
    SetBlockKind:   (range: EditorRange, kind: BlockKind) =>
        ({ range, kind }) as SetBlockKindCmd,
    Compound:       (steps: ProseCommand[]) => ({ steps }) as CompoundCmd,
})
```

**Drift from the original plan, with rationale:**

- **`Compound(steps)`** — needed for spanning-range inverses where one step can't capture the multi-segment undo (a spanning delete restores via SplitBlock + Insert + Insert + …). Authors also use it for atomic batches.
- **`RemoveMark(markTag, range)` split out** from `Format` — adding a mark and removing one have asymmetric inverses (remove must restore the prior mark payload if any), and removal targets a tag string rather than a typed `MarkSet` value. Keeping them as one variant blurred this.
- **`Insert` content widened** to `string | ProseNode[]` — one variant covers text and structural inserts (e.g. inserting a `HardBreak` node, or reinserting blocks during inverse construction). The original `(text: string, at)` shape couldn't express the latter.
- **`Format` carries `mark: MarkSet`** rather than a tag string — preserves payload (e.g. `Color("#fa0")`, `Link("…")`) which would otherwise be lost.
- **`SplitBlock` accepts `{ newBlockId? }`** so callers (notably the `MergeBlock` inverse) can pin the new block's ID — required for inverse anchor stability and for collaborative editing later.

Authors extend via `ProseCommand.merge({ ... })` (v0.3.10 union algebra). The recommended type alias on the merged form is `Union<typeof ExtendedCommand>`.

**Per-variant grouping metadata for history (v0.4.1):** commands carry `groupKey` and `groupWindow` on their payload when they participate in debounce-grouping. v0.4.0 does not implement history yet — these fields are reserved for v0.4.1's history layer.

#### 3.2 — Default `apply`

`defaultApply` matches over the full ten-variant union. Each arm returns `Validation<ApplyResult<DocumentState, ProseCommand>, CommandError>` — `Valid({ next, inverse })` to commit, `Invalid([…])` to reject. Inverses are produced inline:

```ts
import { match } from "aljabr"

export const defaultApply: CommandProtocol<DocumentState, Document, ProseCommand>["apply"] =
    (state, cmd) =>
        match(cmd, {
            SetCursor:      (c) => applySetCursor(state, c),
            Insert:         (c) => applyInsert(state, c),
            DeleteBackward: ({ range }) => applyDeleteRange(state, range, "backward"),
            DeleteForward:  ({ range }) => applyDeleteRange(state, range, "forward"),
            Format:         ({ mark, range }) => applyFormatRange(state, mark, range, "add", markTag(mark)),
            RemoveMark:     ({ markTag: t, range }) => applyFormatRange(state, undefined as never, range, "remove", t),
            SplitBlock:     (c) => applySplitBlock(state, c),
            MergeBlock:     (c) => applyMergeBlock(state, c),
            SetBlockKind:   ({ range, kind }) =>
                getTag(range) === "Node"
                    ? applySetBlockKindNode(state, (range as { nodeId: string }).nodeId, kind)
                    : applySetBlockKind(state, ProseCommand.SetBlockKind(range, kind)),
            Compound:       ({ steps }) => applyCompound(state, steps),
        })
```

**Spanning ranges are fully supported.** Range commands (`DeleteBackward`/`DeleteForward`/`Format`/`RemoveMark`/`SetBlockKind`) accept any `EditorRange`, including `Text` ranges that cross block boundaries and `Node` ranges. Spanning inverses are emitted as `Compound` of per-segment inverses in reverse order.

**Normalize-on-read.** `defaultApply` does *not* call `normalizeText` on its output — the model deliberately preserves text fragmentation produced by edits (e.g. an `Insert` between two same-marked Texts leaves three Text nodes). Consumers call `normalizeText` from `tree-ops` when they need a canonical form. This keeps inverse anchors stable: a node ID referenced by an inverse is guaranteed to still exist in the immediate `next` state.

**Authors extending the command union** compose with `match()` and `[__]` fallback. The pattern at the end of Phase 3 is:

```ts
import { match, __, type Union } from "aljabr"
import { Dispatcher, Validation } from "aljabr"
import { ProseCommand, defaultApply, type DocumentState, type Document } from "aljabr/ui/prose"

const ExtendedCommand = ProseCommand.merge({
    InsertMention: (userId: string, at: RangePoint) => ({ userId, at }),
})
type ExtendedCommand = Union<typeof ExtendedCommand>

const extendedProtocol: CommandProtocol<DocumentState, Document, ExtendedCommand> = {
    extract: (state) => state.doc,
    apply: (state, cmd) =>
        match(cmd, {
            InsertMention: ({ userId, at }) => /* return Validation.Valid({ next, inverse: ProseCommand.DeleteForward(...) }) */,
            // Fallback narrows to "everything except InsertMention" — i.e. ProseCommand —
            // but TS can't infer that, so we coerce when handing off.
            [__]: (c: ExtendedCommand) => defaultApply(state, c as ProseCommand),
        }),
}

const d = Dispatcher.create(initialState, extendedProtocol)
d.dispatch(ExtendedCommand.InsertMention("alice", at))  // works without call-site casts
```

Inverses are themselves variants of the (possibly extended) command union. Undoing goes through the same dispatch pipeline as forward commands.

#### 3.3 — `proseProtocol`

The default protocol bundles `defaultApply` with the extract function:

```ts
export const proseProtocol: CommandProtocol<DocumentState, Document, ProseCommand> = {
    extract: (state) => state.doc,
    apply:   defaultApply,
}
```

Authors who don't extend the command union pass `proseProtocol` directly to `Dispatcher.create`.

#### 3.6 — Additive revisions (land alongside Phase 4)

The Phase 1 revisions (List/ListItem/BlockEmbed/InlineEmbed variants; Image removal) require additive changes to the command union and `defaultApply`:

**New list-operation commands.** Four variants extend `ProseCommand`:

```ts
export type ToggleListCmd      = Variant<"ToggleList",      { range: EditorRange; ordered: boolean }>
export type IndentListItemCmd  = Variant<"IndentListItem",  { range: EditorRange }>
export type OutdentListItemCmd = Variant<"OutdentListItem", { range: EditorRange }>
export type SplitListItemCmd   = Variant<"SplitListItem",   { at: RangePoint }>
```

- `ToggleList` wraps the blocks in `range` into a `List` (or unwraps if they're already in one). Inverse: `ToggleList` with the same range and the prior `ordered` state.
- `IndentListItem` / `OutdentListItem` adjust the nesting level of a list item. Indent moves the item into the previous sibling's nested list (creating one if needed); outdent promotes it out of its enclosing list. Inverses are each other.
- `SplitListItem` is the Enter-inside-list-item behaviour — splits the current list item into two siblings. Inverse: `MergeBlock` against the new boundary (or equivalent `Compound`).

**Existing range-spanning commands** (`DeleteBackward`/`DeleteForward`/`Format`/`RemoveMark`/`SetBlockKind`) extend to traverse `List` and `ListItem` containers per their existing block-traversal logic. The walk treats `List` as a structural container (like `Quote`) and `ListItem` as a block-equivalent.

**Embed payload validation.** `Insert` and `BlockEmbed`/`InlineEmbed` construction inside any command go through the registered embed schema. `defaultApply` accepts the `editor`'s registered `embeds` (passed via `proseProtocol`'s closure or as part of the dispatcher state — exact wiring lands in Phase 4). When a command produces an embed node, the payload is validated against the registered `Schema.variant` for that name; a payload-shape mismatch returns `Invalid([CommandError.Rejected(...)])`.

**Acceptance criteria** (additive to §3.4):

- ✅ Four list commands ship with forward semantics + inverse round-trip.
- ✅ Range commands traverse `List`/`ListItem` correctly.
- ✅ Embed payload validation rejects malformed payloads with structured errors.
- ✅ Tests in `test/ui/prose/commands.test.ts` extended for the new variants and the embed-validation paths.

### Phase 4: `<Prose>` Component and `ProseRenderer`

Phase 4 ships the prose author surface. The author imports `<Prose>` from `aljabr/ui/prose`, hands it a `Dispatcher` (and an embed registry), and the Component encapsulates everything else — its own `ProseRenderer`, the contenteditable DOM, the `beforeinput` translator, and a custom diff cycle from `editor.state().doc` to the DOM.

#### 4.1 — `ProseHost`

`ProseHost` is a strict superset of `DomHost`. It implements every method `DomHost` does, with identical behavior on plain DOM tags (`<div>`, `<button>`, etc.). It additionally handles:

- **Prose intrinsic tags** in the projection — `block`, `heading`, `quote`, `code`, `list`, `listItem`, `text`, `break`, `hr`, `blockEmbed`, `inlineEmbed`. `createElement(tag)` for these produces appropriately-styled DOM (e.g., `heading` with `level: 2` → `<h2>`; `block` → `<p>`; `text` with marks → wrapping `<strong>` / `<em>` etc. per §1.2's DOM mapping). `setProperty` interprets prose-specific props (`level`, `language`, `marks`, `name` + `payload` for embeds).
- **Embed projection** — `blockEmbed` / `inlineEmbed` elements look up the registered render component via the host's embed registry (passed through closure at host creation), validate the payload via `Schema`, and mount the rendered component output inside a `contenteditable=false` wrapper.

`ProseHost.attach(el)` returns `{ root: el, dispose: () => {} }` — identity. Contenteditable setup, the `beforeinput` listener, and the dispatcher subscription live in the `<Prose>` Component's `mounted` callback (§4.2), not in `attach`. The reason: `attach` is one-time-per-mount, but the dispatcher binding can change across renders (the `state` prop on `<Prose>` is reactive); coupling lifecycle to the `mounted` callback's Scope is the right granularity.

`ProseHost` is constructed with a registry argument: `ProseHost.create({ embeds })`. The lowercase `proseHost` global singleton does **not** exist (unlike `DomHost` and `CanvasHost`) because `ProseHost` carries the embed registry. Each `<Prose>` instance creates its own `ProseHost` with its own registry.

#### 4.2 — `<Prose>` Component

```tsx
import { Dispatcher, match, defer } from "aljabr"
import {
    Prose,
    proseProtocol,
    parse,
    ProseCommand,
    type DocumentState,
    type Document,
} from "aljabr/ui/prose"

const initial = match(
    parse.jsx(
        <document>
            <block><text>Hello, world.</text></block>
        </document>
    ),
    {
        Valid:       ({ value })  => value,
        Invalid:     ({ errors }) => { throw new Error(`parse.jsx failed: ${JSON.stringify(errors)}`) },
        Unvalidated: ()           => { throw new Error("unreachable") },
    },
)

const editor = Dispatcher.create(initial, proseProtocol)

const Bold = () => (
    <button onClick={() => editor.dispatch(
        ProseCommand.Format(MarkSet.Bold(), editor.state().cursor)
    )}>
        B
    </button>
)

// Authors mount via any renderer — DomRenderer is the common case.
const r = DomRenderer.create()
r.mount(() => (
    <div class="editor-shell">
        <Bold />
        <Prose state={editor} />
    </div>
), document.body)
```

`<Prose>` is a JSX Component (not an intrinsic). Its body produces a `<div contenteditable>` view node with a `mounted` callback that:

1. Creates a `ProseRenderer` over the mounted div: `ProseRenderer.create({ embeds })`.
2. Mounts the projection: `r.mount(() => projectDoc(editor.state().doc), el)`.
3. Attaches the `beforeinput` listener — the translator that maps DOM input events to `ProseCommand` variants and dispatches them through `editor.dispatch(...)`.
4. Defers cleanup of all of the above via the `mounted` Scope.

The `<Prose>` body is roughly:

```tsx
export const Prose = <Cmd extends ProseCommand>({
    state,
    embeds,
    readonly,
}: {
    state: Dispatcher<DocumentState, Document, Cmd>
    embeds?: EmbedRegistry
    readonly?: boolean
}) => view("div", {
    contentEditable: !readonly,
    mounted: (el) => {
        const r = ProseRenderer.create({ embeds: { ...DEFAULT_EMBEDS, ...embeds } })
        const unmount = r.mount(() => projectDoc(state.state().doc), el)

        const handler = (e: InputEvent) => {
            e.preventDefault()
            const cmd = translateBeforeInput(e, state.state())
            if (cmd !== null) state.dispatch(cmd as Cmd)
        }
        el.addEventListener("beforeinput", handler)

        defer(() => {
            el.removeEventListener("beforeinput", handler)
            unmount()
        })
    },
})
```

`projectDoc(doc: Document): ViewNode` walks the document tree and emits prose-intrinsic JSX (`view("block", ..., ...)` etc.) which `ProseHost` realizes as DOM. The projection runs as a function child — when `editor.state()` notifies, the function re-runs and the reconciler diffs against existing DOM.

**Lifecycle isolation:** the `ProseRenderer` instance lives entirely inside the Component. The parent renderer (DomRenderer in the example) sees only the contenteditable `<div>` and its `mounted` hook — it has no awareness of prose internals. The prose diff cycle is driven by `editor.state()` notifications, not by the parent renderer's reactive cycle. This satisfies the lifecycle-isolation goal that motivated keeping `ProseRenderer` as a real renderer rather than collapsing it into a binding helper.

#### 4.3 — `ProseRenderer.create` and the Projection

```ts
ProseRenderer.create({ embeds }: { embeds?: EmbedRegistry } = {}): {
    view: typeof view
    mount: (fn: () => ViewNode, container: Element) => () => void
}
```

`ProseRenderer.create` is `Renderer.create(ProseHost.create({ embeds }))` plus the embed-registry plumbing. The returned `mount(fn, container)` matches the universal mount signature — `fn` is the projection function, `container` is the DOM element to render into (typically the contenteditable div from `<Prose>`'s `mounted`).

`projectDoc` is exported from `aljabr/ui/prose` for authors who want to bypass `<Prose>` and drive a `ProseRenderer` directly (rare; the Component is the normal path).

#### 4.4 — `beforeinput` translator

`translateBeforeInput(event, state)` maps `inputType` codes to `ProseCommand` variants. v0.4.0 covers:

| `inputType` | `ProseCommand` |
|---|---|
| `insertText` | `Insert(content, at: state.cursor.point)` |
| `insertParagraph` | `SplitBlock(at, ...)` |
| `insertLineBreak` | `Insert(HardBreak, at)` |
| `deleteContentBackward` | `DeleteBackward(state.cursor)` |
| `deleteContentForward` | `DeleteForward(state.cursor)` |
| `deleteWordBackward` | `DeleteBackward(extendedRange)` |
| `deleteWordForward` | `DeleteForward(extendedRange)` |
| `historyUndo` / `historyRedo` | (deferred to v0.4.1's history layer; ignored in v0.4.0) |
| paste / composition events | (deferred to v0.4.1) |

The translator is a pure function — given an event and the current `DocumentState`, returns `ProseCommand | null`. Returning `null` indicates an unhandled input type; the Component swallows the event (default already prevented) and logs in dev mode.

#### 4.5 — Embed Registry

```ts
type EmbedDefinition<P = unknown> = {
    schema: Schema<P>
    placement: "block" | "inline"
    render: (payload: P) => ViewNode
}

type EmbedRegistry = Record<string, EmbedDefinition>
```

Authors pass the registry to `<Prose embeds={{ … }} />`. The default registry includes `image`:

```ts
const DEFAULT_EMBEDS: EmbedRegistry = {
    image: {
        schema: Schema.object({
            src:     Schema.string(),
            alt:     Schema.string().nullable(),
            caption: Schema.string().nullable(),
        }),
        placement: "block",
        render: ({ src, alt, caption }) => view("img", { src, alt: alt ?? "" }),
    },
}
```

Author registrations example:

```ts
<Prose
    state={editor}
    embeds={{
        reaction: {
            schema:    Schema.object({ emoji: Schema.string() }),
            placement: "inline",
            render:    ({ emoji }) => view("span", { class: "reaction-chip" }, emoji),
        },
        videoCard: {
            schema:    Schema.object({ src: Schema.string(), poster: Schema.string().nullable() }),
            placement: "block",
            render:    VideoCardComponent,
        },
    }}
/>
```

`ProseHost.createElement("blockEmbed" | "inlineEmbed")` looks up `name` in the registry, validates `payload` with the registered `schema`, and mounts `render(payload)` inside a `contenteditable=false` wrapper. Payload-validation failure produces a structured error visible in dev tools and a placeholder DOM node in production.

`parse.jsx` (Phase 7) consults the same registry to recognize JSX tags that map to registered embeds.

#### 4.6 — Type-safe registry via module augmentation

The prose JSX runtime declares a `ProseEmbeds` interface authors augment:

```ts
declare module "aljabr/ui/prose" {
    interface ProseEmbeds {
        reaction:  { emoji: string }
        videoCard: { src: string; poster: string | null }
    }
}
```

The runtime computes `IntrinsicElements` as `{ ...builtins, ...ProseEmbeds }`, so `<reaction emoji="🔥" />` and `<videoCard src="…" poster={null} />` are typed at the JSX level. The registry passed at runtime is checked against the same shape — `Record<keyof ProseEmbeds, EmbedDefinition<ProseEmbeds[Name]>>`. One source of truth, no codegen.

### Phase 5: Synthetic Events

#### 5.1 — The Event Surface

Authors never see raw DOM events. The Component translates every browser event into a synthetic event surfaced via `<Prose>` prop callbacks:

| Synthetic event | Fires when | Carries |
|---|---|---|
| `onInput` | The author's text was inserted/deleted | `{ command: ProseCommand, range: EditorRange }` |
| `onSelect` | Selection changed (collapse, drag, arrow-key navigation) | `{ range: EditorRange, prev: EditorRange }` |
| `onFocus` | Editor gained focus | `{ range: EditorRange \| null }` |
| `onBlur` | Editor lost focus | `{ range: EditorRange \| null }` |

`onPaste` and `onCompose` ship in v0.4.1 alongside paste sanitization and IME handling — they need infrastructure (paste schema, composition state machine) that v0.4.0 does not yet have.

**No `onKeyDown`, no `onKeyPress`, no `onMouseDown`.** Keyboard shortcuts are bound through the `bindings` prop (v0.4.1); pointer interactions translate to `SetCursor` commands; click-to-position is native browser behaviour synced via `selectionchange`.

#### 5.2 — Acceptance Criteria

- `<Prose>` accepts all four synthetic event props with correctly typed payloads.
- Each event fires at the correct moment and carries the documented payload (covered by `test/ui/prose/synthetic-events.test.ts`).
- Authors who don't supply event handlers see no overhead — the event-fan-out is gated on prop presence.

### Phase 6: Native Selection Binding

#### 6.1 — The Sync Loop

Two directions:

- **Model → DOM:** when `editor.state().cursor` changes (via `SetCursor` or any other command), the `<Prose>` Component sets the browser's `Selection` to match. Implementation: locate the DOM nodes corresponding to the `RangePoint`'s `nodeId`s, compute the DOM offsets from the logical character offsets, call `selection.setBaseAndExtent`.
- **DOM → Model:** the Component listens for `selectionchange` on the document while it is mounted. On each fire, it reads the current browser `Selection`, converts the DOM nodes/offsets back to `RangePoint`s, and dispatches a `SetCursor` command at `editor`.

The dispatched `SetCursor` updates the `Dispatcher`'s state, which would normally trigger the model→DOM sync — but the Component guards against the loop by checking whether the incoming `SetCursor` matches the current browser selection. If it does (the model is just catching up to the DOM), the model→DOM sync is skipped.

#### 6.2 — Why Native (Phase Recap)

Browser-native selection ships in v0.4.0 because reimplementing word-boundary navigation, IME caret positioning, and OS-specific keyboard semantics is enormous and almost always wrong on at least one platform. Custom-drawn selection (multi-cursor, collaborative cursors, selections that survive blur) is a v0.5.0 feature added on top — without rewriting the local selection model.

The `<remoteSelection>` overlay primitive that v0.5.0 will introduce *does not* replace browser selection. It overlays additional selections (other users' cursors) on top of the native one.

#### 6.3 — Acceptance Criteria

- Dispatching `SetCursor(range)` (or any other command that produces a new cursor as part of its next-state) updates the browser `Selection` to match.
- Dragging a selection in the DOM dispatches a `SetCursor` command with the corresponding `EditorRange.Text`.
- Clicking on a void node (e.g., a `BlockEmbed("image", ...)` rendered surface, or `<hr>`) dispatches `SetCursor` with `EditorRange.Node(nodeId)`.
- The two sync directions do not loop — `selectionchange` fires from a model-driven DOM update do not re-dispatch.
- A test file `test/ui/prose/selection.test.ts` covers each of the above with JSDOM.

### Phase 7: `parse.jsx` and Read-Only Mode

#### 7.1 — `parse.jsx`

A namespace export. v0.4.0 ships only `parse.jsx`; `parse.text`, `parse.html`, `parse.json` ship in v0.4.2.

```ts
import { parse } from "aljabr/ui/prose"
import { match } from "aljabr"

const result = parse.jsx(
    <document>
        <block><text>Hello, world.</text></block>
    </document>
)
// result: Validation<DocumentState, DecodeError>

const initial = match(result, {
    Valid:       ({ value })  => value,
    Invalid:     ({ errors }) => { throw new Error(`bad JSX: ${JSON.stringify(errors)}`) },
    Unvalidated: ()           => { throw new Error("unreachable") },
})
```

`parse.jsx` walks a JSX tree of prose primitives and returns `Validation<DocumentState, DecodeError>`. The tree is validated against the closed structural set plus the registered embeds (default registry + author registrations passed as a second arg, or via the `<Prose embeds>` prop at runtime). Unknown elements (`<paragraph>`, `<bold>`, an HTML element with no embed registration) produce an `Invalid` with structured errors pointing to the offending node. Marks on `<text>` are extracted (built-in props plus the `marks` record) and merged into the variant payload.

**Registry-aware tag resolution.** Tags that match a registered embed name resolve to `BlockEmbed` / `InlineEmbed` nodes with the validated payload. The default `image` registration means `<image src="…" alt="…" caption="…" />` parses to `BlockEmbed("image", { src, alt, caption })` out of the box. Author registrations (e.g., `reaction`, `videoCard`) become valid JSX tags after module augmentation (Phase 4 §4.6) — `parse.jsx` consults the same registry the runtime renderer uses.

```ts
parse.jsx(node, embeds?: EmbedRegistry): Validation<DocumentState, DecodeError>
```

The `embeds` argument defaults to the package's default registry. Authors with custom embeds pass the same registry they use on `<Prose>`.

**Why `Validation` rather than throw:** consistency with `parse.text`, `parse.html`, `parse.json` (v0.4.2). All four parsers share one return type so call sites read the same way regardless of source.

The namespace shape (`parse.jsx`, `parse.text`, ...) parallels `Schema.string`, `Schema.object`, `is.any` — same idiomatic export style used elsewhere in aljabr.

#### 7.2 — `readonly` Prop

```tsx
<Prose state={editor} readonly />
```

When `readonly`:

- The `contenteditable` attribute is set to `false` on the root `<div>` produced by `<Prose>`.
- The `beforeinput` listener is not attached.
- The cursor caret is hidden (CSS `caret-color: transparent`).
- `selectionchange` continues to dispatch `SetCursor` (so highlight UIs work for copying).
- Programmatic `editor.dispatch(...)` still applies — authors can hydrate read-only documents at any time.

`readonly` is a runtime-toggleable prop. The Component re-evaluates the `contenteditable` attribute and listener attachment on every prop change without rebuilding the document tree. Toggling is cheap.

**Why a prop, not a separate component or package:** bundle-size savings of a separate `<ProseView>` are negligible (the command pipeline is small); the ergonomic cost of forcing component-swapping for runtime read-only/editable toggles (e.g., comment threads where editing your own comment becomes available on hover) is real.

#### 7.3 — Acceptance Criteria

- `parse.jsx(<document>…</document>)` returns `Valid(state)` carrying a `DocumentState` with the correct tree, marks, embed nodes, and node IDs.
- Default `<image>` and author-registered embed tags resolve to `BlockEmbed`/`InlineEmbed` with payloads validated by the registered `Schema`.
- Unknown JSX elements (`<paragraph>`, `<bold>`, an unregistered tag) return `Invalid(errors)` with structured `DecodeError` entries pointing at the offending node, the closed structural set, and the registered embed names.
- `<Prose state={editor} readonly>` mounts without contenteditable, suppresses `beforeinput` dispatch, and continues to render the document tree reactively.
- Toggling `readonly` at runtime updates the contenteditable attribute and command-dispatch behaviour without remounting the document tree.
- Tests in `test/ui/prose/readonly.test.ts` and `test/ui/prose/parse-jsx.test.ts` cover: parse default + author-registered embeds, payload validation failure paths, render, toggle, programmatic dispatch in readonly mode, selection-only cursor changes.

Deferred to v0.4.2. The default `image` embed registration is supported from v0.4.0 — but inserting one via drag-and-drop or upload is a v0.4.2 ergonomic concern.

#### 8.6 — Plugin / middleware architecture

Considered during the prose-design grilling and rejected. Author extension uses `ProseCommand.merge` plus `match()`-with-`[__]` composition — no separate plugin system. If demand for third-party packaged extensions emerges, a thin convention (a "prose plugin" is just a function that returns a partial command set + apply override + bindings + paste schema fragment) can be added without changing the core surface.

#### 8.7 — Spell-check, autocorrect, accessibility (ARIA, screen readers)

Default browser behaviours pass through where they don't conflict with the model-owned-DOM thesis: spell-check is opt-in via `<Prose spellcheck>`; autocorrect on iOS comes through composition events (handled in v0.4.1's IME work). ARIA roles for the editor surface, blocks, and headings are auto-applied (`role="textbox"` on the `<Prose>` root `<div>`, `role="heading"` with `aria-level` on `<heading>`). Screen-reader-specific testing ships as part of v0.4.1's IME work because IME and screen reader interactions overlap.

#### 8.8 — Editable structured embeds (compound nodes with editable slots)

Deferred to v0.4.x. v0.4.0's `BlockEmbed`/`InlineEmbed` are *void* — selected and deleted as a unit, no internal editable text. Editable structured embeds (callout cards with editable title + body, code-playground cards with editable code regions, comment threads with editable replies) require ProseMirror-style "node views with content holes": selection traversal across slot boundaries, command dispatch into nested editable regions, schema for valid contents per slot. Real complexity in its own right; ships in a later v0.4.x release once void embeds are validated by real consumers.

#### 8.9 — Tables

Deferred to v0.4.x or v0.5.0. Tables (table, row, cell, header cell, column-span/row-span) require their own selection model (rectangular selection, column-/row-based commands), navigation rules (Tab moves to next cell), and accessibility surface (ARIA grid roles). Out of scope for v0.4.0; revisited once lists ship and inform the structural-extension pattern.

---

### Design Constraints

- **Prelude consumption only.** v0.4.0 builds on v0.3.10's `Dispatcher`, `CommandError`, and union algebra. No further prelude additions.
- **Renderer abstraction rebuild.** `aljabr/ui/{renderer,types,dom,canvas}` are reshaped in Phase 0 — the legacy `createRenderer` / `createCanvasRenderer` exports are removed in favor of `Renderer.create` + capitalized stateless hosts + thin `<Type>Renderer.create()` wrappers + `<Canvas>` Component. Demos under `public/` migrate.
- **Closed structural set + open embed extension.** Structural primitives (Document, Block, Heading, Quote, Code, List, ListItem, Text, HardBreak, Hr) are closed. Author-defined *content* (videos, charts, custom widgets) is registered via the embed registry. The split aligns extension surface to the actual extension axis authors need.
- **Native selection only.** Custom selection rendering is v0.5.0.
- **No external dependencies introduced.** Implementation uses prelude primitives, browser APIs, and the existing `aljabr/ui` reconciler.
