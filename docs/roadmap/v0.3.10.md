### **Aljabr Roadmap (v0.3.10): Prelude Foundations for Command-Driven State**

**Strategic Vision**

v0.3.x is converging on a long-deferred opportunity: a contenteditable-replacement renderer for text editing (`aljabr/ui/prose`, lifting off in v0.4.0). That renderer needs a reactive primitive that goes beyond `Signal`'s "set replaces state" model — every write must be a discrete, validated, named operation so authors get history, undo/redo, transactional rejection, and (eventually) collaborative transforms for free.

Rather than ship that primitive privately inside `prose`, v0.3.10 lifts it into `prelude` alongside `Signal`, `Ref`, and `Derived`. The pattern — *validated transactional writes against a reactive state* — is genuinely general (form validation, multi-step wizards, state machines with rejectable transitions) and earns its place next to the existing primitives. The prose renderer becomes the first production consumer; future authors writing non-UI domain logic get the same machinery for free.

This release also lands a small but long-overdue ergonomic on `union()`: algebraic operations to compose, narrow, and project union types without the spread-and-reapply-impls dance. The prose command surface depends on it (every prose author will extend the built-in command union with their own variants), but the operations are useful anywhere unions are extended — refactoring a domain ADT, slicing a feature flag enum, narrowing a result type for a public API.

The release is internally self-contained. The renderer surface (`aljabr/ui`, `aljabr/ui/dom`, `aljabr/ui/canvas`) is unchanged. No prose code lands here — that begins in v0.4.0.

### Phase 1: `Dispatcher`

#### 1.1 — The Gap

`Signal<T, S>` today supports a custom state union via `SignalProtocol<S, T>` — but the protocol only defines how to *read* `T` out of `S` (`extract`) and which states are terminal (`isTerminal`). Writes are direct state replacement: `signal.set(newState)` overwrites whatever was there, with no chance to validate, transform, or reject.

That model is correct for the cases `Signal` already serves (lifecycle states, simple custom unions), but it cannot host:

- **Validated writes**: "this transition is illegal in the current state"
- **Discrete write history**: any reasonable undo stack needs a typed name for what changed
- **Collaborative transforms**: operational transformation requires writes to be discrete, named, transformable values
- **Rejectable transactions**: an editor needs to reject a paste that would create an invalid document tree

Prose needs all four. So does any state machine with non-trivial transition rules. `Dispatcher` is the primitive that supplies them.

**Why not `CommandSignal`:** an earlier draft of this roadmap called the primitive `CommandSignal`. The name was rejected because (a) it reads as a sibling of `Signal`, but the read API and write protocol diverge enough that the name misleads, and (b) the primitive is a reactive container whose interaction model is "dispatch a discrete operation," and `Dispatcher` says exactly that. The author-written part — the `extract`/`apply`/`isTerminal` triple — keeps the `Protocol` family name (`CommandProtocol`).

#### 1.2 — Shape

```ts
type ApplyResult<S, Cmd> = {
    next: S
    inverse: Cmd
}

type CommandProtocol<S, T, Cmd> = {
    extract: (state: S) => T | null
    apply: (current: S, command: Cmd) => Validation<ApplyResult<S, Cmd>, CommandError>
    isTerminal?: (state: S) => boolean
}

class Dispatcher<T, S, Cmd> {
    static create<T, S, Cmd>(initial: S, protocol: CommandProtocol<S, T, Cmd>): Dispatcher<T, S, Cmd>

    dispatch(command: Cmd): Validation<ApplyResult<S, Cmd>, CommandError>
    get(): T | null         // untracked extracted value
    state(): S              // tracked full state
    peekState(): S          // untracked full state
    dispose(): void
}
```

Key design notes:

- **`apply` produces both the next state and an inverse command in one pass.** The `Validation<ApplyResult, CommandError>` shape lets the protocol either commit a state transition (with its inverse, ready for any consumer who wants to log it) or reject with a structured error list. This is the foundation for every higher-level feature: history (just store inverses), undo (dispatch an inverse), validation (return `Invalid` from `apply`).

- **`dispatch` returns the validation.** Authors decide whether to inspect failures or fire-and-forget. Most editor-side dispatches will ignore the return value (the renderer surfaces failures via `onInput` events); validation-heavy domains pattern-match on the return.

- **The protocol is a strict superset of `SignalProtocol`.** The `extract` and `isTerminal` slots are the same; `apply` is added. A `Dispatcher` whose `apply` is a pure state replacement (`(_, cmd) => Validation.Valid({ next: cmd, inverse: ??? })`) degenerates to `Signal` semantics, but the inverse requirement means there's always a story for undoing.

- **`Cmd` is author-supplied.** The library does not ship a base `Command` union, namespace, or builder helpers. Authors define their own with `union(...)`. The compile-time relationship between `Cmd` and `apply` is enforced through the generic, not through a marker type or trait.

#### 1.3 — Implementation Strategy Options

| Option | Approach | Notes |
|---|---|---|
| 1 | **Extend `Signal<T, S>` to `Signal<T, S, Cmd>` with an optional `apply` slot.** The same class handles both modes; `dispatch` is undefined when no `apply` is supplied. | Keeps one primitive; bloats the `Signal` type signature for every consumer who never uses commands. The `Cmd` parameter shows up in autocomplete and error messages even in the non-command path. **Rejected.** |
| 2 | **Sibling primitive: `Dispatcher`.** Internal implementation may share a base class, but the public type is distinct. `Signal` stays at two type parameters. | Author-facing surface stays clean. Discoverability lands on a name whose interaction model ("dispatch a discrete operation") is in the name itself. |
| 3 | **Wrapper helper that adds `dispatch` to an existing `Signal`.** `withCommands(signal, apply)` returns a `{ dispatch, get, state }` object. | Lightest implementation. But the wrapper isn't a `Signal` itself — consumers expecting reactive `state()` from a `Signal` need a different access pattern, fragmenting the API. |

**Recommendation: Option 2 (sibling primitive).** Best ergonomics, preserves `Signal`'s simplicity, makes the new capability discoverable. Internal implementation should share the dependency-tracking and disposal machinery with `Signal` to avoid duplicating subscription bookkeeping; that's a code-organisation question, not a public-API one.

#### 1.4 — Acceptance Criteria

- `Dispatcher.create(initialState, protocol)` returns a dispatcher whose `dispatch(cmd)` routes through `protocol.apply` and returns the resulting `Validation`.
- A successful `dispatch` updates the internal state to `result.next` and notifies dependents.
- A failed `dispatch` (`Validation.Invalid`) leaves the state unchanged and does not notify dependents.
- `state()` is a tracked read; `peekState()` is untracked. `get()` extracts the value via `protocol.extract`.
- The dispatcher disposes cleanly via `dispose()`; subsequent `dispatch` calls error.
- A new test file `test/prelude/dispatcher.test.ts` covers: successful dispatch, rejected dispatch, inverse round-trip (dispatch → dispatch inverse → state matches original), tracked vs untracked reads, disposal, and termination via `isTerminal`.
- Documentation under `docs/api/prelude/dispatcher.md` describes the protocol, lifecycle, and three illustrative examples (form field with validation; counter with bounded transitions; document state with insert/delete commands).

### Phase 2: `CommandError`

#### 2.1 — The Gap

`apply()` returns `Validation<_, CommandError>`, so `CommandError` is part of the public type signature of every `Dispatcher`. If it were author-defined per-domain, every consumer of `Dispatcher` would have a different error type and the type cross-compatibility story (e.g., a generic history middleware that works across domains) collapses.

Standardising `CommandError` as a published union — extensible via `.merge()` — means:

- All domains return the same base error shape; cross-domain tooling (history wrappers, dev-tools panels, error reporters) speaks one vocabulary.
- Authors extend with domain-specific failure variants where they need to without forking the type.
- The error union is typed exhaustively; `match()` on it never silently drops a case.

#### 2.2 — Shape

```ts
const CommandError = union({
    Rejected: (reason: string) => ({ reason }),
    Conflict: (detail: string) => ({ detail }),
    Invalid:  (errors: DecodeError[]) => ({ errors }),
})
```

Three base variants, each with a clear semantics:

- **`Rejected`** — the command is structurally fine but the protocol declined to apply it (e.g., "cannot insert into a void node"). Carries a human-readable reason.
- **`Conflict`** — the current state is incompatible with the command (e.g., "command targets a node ID that no longer exists"). Carries a detail string for diagnostics.
- **`Invalid`** — the command's payload failed schema validation. Carries the existing `DecodeError[]` from `aljabr/schema`.

Authors extend via `.merge()` (Phase 3):

```ts
const ProseCommandError = CommandError.merge({
    BoundaryViolation: (range: EditorRange) => ({ range }),
    SchemaConflict:    (detail: string) => ({ detail }),
})
```

#### 2.3 — Acceptance Criteria

- `CommandError` is exported from `aljabr/prelude`.
- The three base variants serialize cleanly via the existing `aljabr/schema` `Schema.variant` builders (the prose paste pipeline depends on this in v0.4.1).
- A new test file `test/prelude/command-error.test.ts` covers: variant construction, `match()` exhaustiveness, `.merge()` extension produces a union compatible with `apply()` return signatures.
- Documentation under `docs/api/prelude/command-error.md` describes when each variant fits and shows the extension pattern.

### Phase 3: Union Algebra

#### 3.1 — The Gap

Today, extending a union requires the spread-and-reapply pattern:

```ts
const BaseCommand = union({ Insert: ..., Delete: ... })

// To extend: spread the original factories into a new union, manually re-list impls
const BaseFactories = { Insert: ..., Delete: ... }  // duplicated
const ExtendedCommand = union([...baseImpls, NewImpl])({
    ...BaseFactories,
    InsertMention: ...,
})
```

This has four problems:

1. The original factories object isn't recoverable from `BaseCommand` — there's no `.config` getter on the union value. Authors keep a separate reference.
2. Impls don't compose. The base impl array must be threaded through manually.
3. Overlapping keys silently override (whichever appears last wins) — no compile-time warning.
4. There's no story for narrowing a union — you cannot `pick` a subset of variants for a more constrained API surface.

Prose lives or dies on author-extensible commands, so every author writing a domain editor will hit problems 1–3 in their first hour. The fix is small, mostly type-level, and useful far beyond prose.

#### 3.2 — Shape

The value returned by `union()` gains three method properties (and stores its raw `factories` and `impl` arrays under new internal symbols `factoriesTag` and `implsTag` — non-enumerable, alongside the existing `unionFactoryTag`):

```ts
interface UnionResult<F, I> {
    [variantName]: VariantFactory  // existing — unchanged
    
    // New: store the raw inputs for composition (non-enumerable)
    [factoriesTag]: F
    [implsTag]: I

    // Algebra — `.merge` mirrors the curried `union([Impl])(factories)` form
    merge<F2>(factories: NoOverlap<F, F2>): UnionResult<F & F2, I>
    merge<I2 extends AbstractConstructor[]>(impls: I2): {
        (factories: NoOverlap<F, F2 extends Record<string, any> ? F2 : {}>): UnionResult<F & F2, [...I, ...I2]>
    }
    pick<K extends keyof F>(...keys: K[]): UnionResult<Pick<F, K>, I>
    omit<K extends keyof F>(...keys: K[]): UnionResult<Omit<F, K>, I>
}
```

The two `.merge` overloads mirror the existing `union()` overloads:

```ts
// Direct form — extend variants, keep existing impls
const ProseCommandWithKeys = ProseCommand.merge({
    KeyPress: (key: string, modifiers: string[]) => ({ key, modifiers }),
})

// Impl form — extend with additional impl mixins, then variants
const TrackedCommand = ProseCommand.merge([Trackable])({
    Logged: (msg: string) => ({ msg, id: "" }),
})
```

Where `NoOverlap<F, F2>` is a TypeScript utility that errors at compile time if any key in `F2` already exists in `F`:

```ts
type NoOverlap<F, F2> = {
    [K in keyof F2]: K extends keyof F
        ? never & { __error: `Key "${K & string}" already exists in union; use .omit("${K & string}").merge(...) to replace` }
        : F2[K]
}
```

**Why these three operations and not the full set algebra:**

- `merge` (∪) is the commonest operation: extend a union with new variants. **Required.**
- `pick` selects a subset (useful for narrowing a public API surface, e.g., a "user-callable commands" subset of the full editor command union). **Required.**
- `omit` is the inverse and the explicit-replacement path: `.omit("Insert").merge({ Insert: ... })` to replace a variant. **Required.**
- `intersect` (∩) on full union types is rarely useful and the typing is tricky (variants with the same name but different payloads). **Skipped.**
- `difference` (A − B) on union *values* is structurally equivalent to `omit` driven by another union's keys — adds API surface for negligible benefit. **Skipped.**

#### 3.3 — Implementation Strategy Options

| Option | Approach | Notes |
|---|---|---|
| 1 | **Mutate the union result object** to add `merge`/`pick`/`omit` as own methods. | Simplest. Each method calls `buildUnion` internally with the appropriate factories/impls combination. Method dispatch is per-instance — cheap. |
| 2 | **Free-standing functions: `merge(unionA, factoriesB)`, `pick(unionA, ...keys)`.** | Less discoverable. Importing `merge` separately fights the "the union is an object you can compose" mental model. |
| 3 | **Builder pattern returning a new builder: `union(...).extend({ ... }).extend({ ... })`** | Verbose for the two-step case; chains poorly with `pick`/`omit`. |

**Recommendation: Option 1 (methods on the union result).** Discoverability and ergonomics both favour it. The only constraint is that `buildUnion`'s output object must store the raw `factories` and `impl` arrays so `merge`/`pick`/`omit` can reconstruct correctly. These ride on Symbol keys (`factoriesTag`, `implsTag`) so they don't pollute `for-in` or `Object.keys` enumerations.

#### 3.4 — Acceptance Criteria

- `BaseUnion.merge({ NewVariant: ... })` returns a new union with all base variants plus the new one.
- `BaseUnion.merge({ Insert: ... })` (when `Insert` is already in `BaseUnion`) is a **type error** at compile time, with a helpful message pointing toward `.omit("Insert").merge(...)`.
- `BaseUnion.pick("Insert", "Delete")` returns a union containing only those two variants; impl array is preserved.
- `BaseUnion.omit("Insert")` returns a union with that variant removed; impl array is preserved.
- Impl arrays are concatenated by `merge` (base impls first, new impls appended) and preserved by `pick`/`omit`.
- Round-trip: `union(F).merge(F2).pick(...keys)` produces a structurally equivalent union to `union(pickKeys(F & F2, keys))`. New tests in `test/union-algebra.test.ts` cover all three operations and the cross-composition.
- The existing `union()` API and runtime behaviour is unchanged for any caller that doesn't use the new methods. All v0.3.x tests in `test/union.test.ts` continue to pass without edits.
- Documentation in `docs/api/union.md` gains an "Algebra" section describing the three methods and the `NoOverlap` constraint.

### Phase 4: `Schema.lazy`

#### 4.1 — The Gap

`aljabr/schema` cannot express recursive schemas today. The internal `_Schema` union has variants for `String`, `Object`, `Variant`, `Array`, etc., but no thunked variant — so a `Schema<T>` definition can never reference itself, even indirectly through one of its fields.

This blocks `documentSchema` in v0.4.2: the prose `<document>` contains `ProseNode` children, and `ProseNode.Document` (along with `Block`, `Heading`, `Quote`, `Code`) carries a `children: ProseNode[]` field. Without recursion, the schema cannot be written at all.

#### 4.2 — Shape

A new `Schema.lazy` factory wrapping a thunk:

```ts
Schema.lazy<T>(thunk: () => Schema<T>): Schema<T>
```

The thunk is evaluated on every decode/encode pass (cheap — just dereferences the schema). Authors use it to break the otherwise-circular reference:

```ts
const proseNodeSchema: Schema<ProseNode> = Schema.variant(ProseNode, {
    Document: Schema.object({
        children: Schema.array(Schema.lazy(() => proseNodeSchema)),
    }),
    Block: Schema.object({
        children: Schema.array(Schema.lazy(() => proseNodeSchema)),
    }),
    Heading: Schema.object({
        level: Schema.number(),
        children: Schema.array(Schema.lazy(() => proseNodeSchema)),
    }),
    // ...other variants
})
```

#### 4.3 — Implementation Strategy

A new `LazySchema` variant inside the internal `_Schema` union, carrying the thunk. The decoder and encoder evaluate the thunk and recurse into the produced schema. No caching is needed — the thunk is a closure dereference, and authors who want memoization can wrap it themselves.

```ts
LazySchema: (thunk: () => unknown) => ({ thunk })
```

In `_decode` / `_encode`, the new arm is one line:

```ts
LazySchema: ({ thunk }) => _decode((thunk as () => AnySchema)(), input, path),
```

#### 4.4 — Acceptance Criteria

- `Schema.lazy(() => mySchema)` returns a `Schema<T>` whose decode/encode behavior matches the thunk's resolved schema.
- A recursive schema definition (e.g., a tree node that contains tree-node children) decodes and encodes a nested example tree successfully.
- `roundtrip(recursiveSchema, input)` returns `true` for valid inputs.
- A new test file `test/schema/lazy.test.ts` covers: basic recursion, mutual recursion (two schemas referencing each other), error path propagation through the lazy boundary.
- Documentation in `docs/api/schema.md` gains a "Recursive Schemas" section.

### Phase 5: API Consistency Migration

#### 5.1 — The Gap

Phases 1–4 added new primitives without disturbing existing ones. But the existing prelude has accumulated drift across versions, and prose (v0.4.0) is the deadline for paying it down: every author building a domain editor will hit the inconsistencies in their first hour.

The audit found drift in five categories:

1. **Construction shape** — five distinct patterns for "make one of these" (static `.create()`, capitalized function, variant factories, namespace builders, lowercase free functions). Authors guess.
2. **Read API** — `state()` is a method on `Signal`/`Dispatcher` and a getter on `Derived`/`AsyncDerived`. `peek` exists everywhere except `Dispatcher`. `AsyncDerived.get()` returns `Promise<T>` while every other `get()` is sync.
3. **Write API** — `Signal.set` returns void, `RefArray.set` returns `Option<T>`. `subscribe` exists only on `Signal`. Disposal is `void` everywhere except `Scope`, with no `Symbol.dispose` adoption anywhere.
4. **Operators on ADTs** — five ad hoc trait classes (`Mappable`, `Combinable`, `Traversable`, `Computable`, `Thenable`) each redefining `map` independently. `Option.getOrElse` uses one verb; nothing else has the equivalent. `Promise.all`-style aggregation has to be hand-written for every type.
5. **Naming** — `Ref` reads as "reference" but the abstraction is a reactive store with per-path tracking. `RefArray` is a two-word name where the rest of the library is one word. `watchEffect` is a two-word coordinator where the rest are one word.

The migration normalizes all five categories. Breaking changes are accepted because v0.3.x is pre-release and the cost of carrying the drift into v0.4.0 (where every prose author depends on the prelude) outweighs the cost of one disruptive release.

The complete style guide lands at `docs/guides/style-guide.md`. This phase is the migration to comply with it.

#### 5.2 — The Four Buckets

Every public abstraction is classified into exactly one of four buckets. The bucket dictates its construction shape, read API, write API, disposal semantics, and operator coverage.

| Bucket | Members |
|---|---|
| **1. Reactive containers** | `Signal`, `Derived` / `WritableDerived`, `AsyncDerived`, `Store`, `List`, `Dispatcher` |
| **2. Algebraic data types** | `Result`, `Option`, `Validation`, `Tree`, `Fault`, `Schedule`, `Effect`, `CommandError`, `DecodeError`; `Schema` (codified DSL exception) |
| **3. Resource / lifetime primitives** | `Scope`, `Resource` |
| **4. Top-level coordinators** | `watch`, `match`, `decode`, `encode`, `batch`, `untrack`, `runInContext`, `defer`, `acquire` |

#### 5.3 — Renames (breaking)

| Before | After | Reason |
|---|---|---|
| `Ref<T>` | `Store<T>` | "Ref" implies reference cell; the abstraction is a reactive store with per-path tracking. Solid/Redux users transfer the mental model immediately. |
| `RefArray<T>` | `List<T>` | One-word name; pairs with `Store`. |
| `watchEffect` | `watch` | One-word coordinator, free of internal collision (unlike `track`, which collides with `trackIn`/`untrack`). |
| `Option.getOrElse` | `Option.getOr` | Single verb across the library for "read with default." |
| `WatchHandle.stop()` | `WatchHandle.dispose()` | Universal disposal idiom. |
| `persistedSignal(initial, opts)` | `Signal.persisted(initial, opts)` | Persistence sits on the namespace it modifies. |
| `syncToStore(signal, opts)` | `signal.persist(opts)` | Instance method; returns `WatchHandle`. |

#### 5.4 — Construction normalization

- `Scope(...)` → `Scope.create(...)`. `Resource(...)` → `Resource.create(...)`. The `signals/` submodule keeps free-function aliases (`scope(...)`, `resource(...)`).
- `Ref.create([...])` array overload removed. `List.create([...])` is the only path to a root reactive array.
- `Derived.create(fn)` for read-only; `Derived.writable({ get, set })` for writable. The latter returns `WritableDerived<T> extends Derived<T>`. A variable typed `Derived<T>` accepts either; only `WritableDerived<T>` exposes `.set()`. Replaces the runtime `"Derived is read-only"` throw with a compile-time error.
- ADTs continue to use variant factories (`Result.Accept`, `Option.Some`, etc.). `Schema` is the codified exception.

#### 5.5 — Read API normalization

Canonical bucket-1 read vocabulary:

| Method | Returns | Tracked? |
|---|---|---|
| `get()` | extracted `T \| null` (lifecycle) or `T \| undefined` (positional) | yes |
| `getOr(default)` | `T` (non-nullable) | yes |
| `peek()` | extracted, same nullability as `get()` | no |
| `state()` | full state union | yes (lifecycle-bearing only) |
| `peekState()` | full state union | no (lifecycle-bearing only) |

Specific changes:

- `Derived.state` and `AsyncDerived.state` getters → `state()` / `peekState()` methods. Tracked + untracked variants like `Signal` and `Dispatcher`.
- `Dispatcher.peek()` added.
- `AsyncDerived.get()` becomes synchronous (`T | null`, tracked, last-known value). New methods: `AsyncDerived.run(): Promise<Done<T, E> | Failed<T, E>>` and `AsyncDerived.runOr(default): Promise<T>` mirroring `Effect.run` / `Effect.runOr`.
- `getOr(default)` added across all bucket-1 reads (Signal, Derived, AsyncDerived, Dispatcher; Store/List use `getOr(path, default)` and `getOr(i, default)`).
- `Store` and `List` keep their `isUnset` getter; no synthetic `state()` invented.
- Nullability rule codified: `null` for lifecycle absence, `undefined` for positional/path absence.

#### 5.6 — Write API normalization

- All structural writes return `void`. `List.set(i, value)` no longer returns `Option<T>` — callers `peek(i)` first if they need the prior value.
- Destructive reads keep `Option<T>` (`pop`, `shift`).
- Transactional writes keep their structured outcome (`Dispatcher.dispatch` → `Validation<ApplyResult, CommandError>`). Codified style-guide exception.
- `Store.push` / `pop` / `splice` / `move` removed. Array mutations live on `List`. Path-based access is `store.at(path)` → `List`.

#### 5.7 — Subscription

- `subscribe(callback): () => void` added on `Derived`, `AsyncDerived`, `Store`, `List`, `Dispatcher`. (`Signal` already has it.)
- Each container's callback receives its `get()` shape (extracted value for value-bearing types; whole snapshot for `Store`; whole array for `List`).
- Granular subscription via `at(path).subscribe()` — no positional overloads on the parent.
- Each container keeps a `#valueSubscribers` Set distinct from the `#subscribers` Map used for tracked computations. The two notification mechanisms have different lifecycles, signatures, and scheduler interactions; merging them costs more than it saves.

#### 5.8 — Disposal

- Sync `void dispose()` on every bucket-1 container and `WatchHandle`. `Symbol.dispose` implemented on each (TC39 explicit resource management):

```ts
using sig = Signal.create(0)
// disposed automatically at block exit
```

- Async `Promise<Defect[]> dispose()` retained on `Scope`. `Symbol.asyncDispose` already implemented.

#### 5.9 — Operator / trait extraction (bucket 2)

The five ad hoc trait classes are refactored into a small set of canonical reusable traits, mixed in via `union([...]).typed({...})`.

| Trait | Methods | Mixed into |
|---|---|---|
| `Mappable<T>` | `map<U>(fn): Self<U>` | every monadic ADT |
| `Bindable<T> extends Mappable<T>` | `flatMap<U>(fn: T → Self<U>): Self<U>` | Option, Result, Validation, Effect |
| `Reducible<T>` | `getOr(default: T): T` | Option, Result, Validation |
| `Foldable<T>` | `fold<U>(fn, initial): U` | Tree |
| `Combinable<T, E>` | `combine(other): Self<...>` | Validation |
| `Thenable<T, E>` | `then`, `catch` | Result |
| `Computable<T, E>` | `run`, `recover` | Effect |

Concrete additions:

- `Result` gains `map`, `flatMap`, `getOr` alongside its existing `then` / `catch`.
- `Validation` gains `flatMap` and `getOr`. `combine` retained for error-accumulating applicative use.
- `Tree` keeps `map` / `fold` / `depth` — no `flatMap` (not naturally chainable).
- Inert ADTs (`Fault`, `Schedule`, `CommandError`, `DecodeError`) stay inert. Codified style-guide rule: descriptor ADTs carry no methods; consumers use `match`.

Static aggregators (`Promise.all`-shaped helpers) added on the namespace:

```ts
Option.all([opt1, opt2])         // fail-fast: None if any None
Result.all([res1, res2])         // fail-fast: Reject on first
Effect.all([eff1, eff2])         // parallel-fail-fast (mirrors Promise.all)
Effect.allSettled([eff1, eff2])  // parallel-collect, returns all settlements
```

`Validation.all` already exists and accumulates errors across Invalids — its semantics are already the Validation-shaped equivalent of `allSettled`. No new variant needed.

`Effect.runOr(default): Promise<T>` added alongside `Effect.run()`.

#### 5.10 — Implementation Strategy

The migration is large but each piece is independent. Land in this order to keep the working tree compilable at every step:

1. **Trait extraction.** Factor `Mappable`, `Bindable`, `Reducible`, `Foldable` into their own file (`src/prelude/traits.ts`). Refactor `Option`, `Result`, `Validation`, `Effect`, `Tree` to mix them in. Existing tests remain green; behaviour unchanged.
2. **Read-API additions (additive, non-breaking).** Add `getOr` everywhere; add `Dispatcher.peek()`; add `state()` / `peekState()` methods alongside the existing getters on `Derived` / `AsyncDerived`. Old getters deprecated but kept for one phase.
3. **Static aggregators.** Add `Option.all`, `Result.all`, `Effect.all`, `Effect.allSettled`, `Effect.runOr`.
4. **Subscription propagation.** Add `subscribe` to `Derived`, `AsyncDerived`, `Store` (rename pending), `List` (rename pending), `Dispatcher`. Mirror Signal's existing implementation.
5. **`Symbol.dispose` adoption.** Add to every disposable container. Non-breaking.
6. **`AsyncDerived` async-shape change (breaking).** `get()` becomes sync; introduce `run()` and `runOr()`. Migration: any caller of `await asyncDerived.get()` becomes `await asyncDerived.run()` (or `.runOr(default)` if a default is acceptable).
7. **Renames (breaking, all-at-once).** `Ref` → `Store`, `RefArray` → `List`, `watchEffect` → `watch`, `Option.getOrElse` → `Option.getOr`, `WatchHandle.stop` → `WatchHandle.dispose`, `persistedSignal` → `Signal.persisted`, `syncToStore` → `signal.persist` (returns `WatchHandle`). Land these together to minimize the migration window for downstream consumers.
8. **`Derived` / `WritableDerived` split (breaking).** `Derived.create({ get, set })` overload removed; `Derived.writable({ get, set })` introduced. Read-only `Derived<T>` no longer has `.set()`. `Derived.state` getter removed (replaced in step 2).
9. **`Store` array-method removal (breaking).** Drop `Store.push` / `pop` / `splice` / `move`. Force callers through `store.at(path)` → `List`.
10. **`List.set` return-type change (breaking).** Returns `void` instead of `Option<T>`. Migration: callers that need the prior value call `list.peek(i)` first.
11. **Construction normalization (breaking).** `Scope()` → `Scope.create()`, `Resource()` → `Resource.create()`. Lowercase free-function aliases added in `signals/`.
12. **Tag the release.** Every breaking step lands behind a single version bump (v0.3.10 → v0.3.11 candidate, finalized as 0.3.10 if all changes ride together; otherwise the migration ships as 0.3.11 and v0.3.10 stays at "Phases 1–4").

The order above keeps the tree green between steps. Steps 1–5 are additive and can land in any order. Steps 6–11 are breaking and should be batched into a single tagged release to avoid forcing downstream consumers through multiple migration passes.

#### 5.11 — Acceptance Criteria

- `docs/guides/style-guide.md` is published and describes every rule in this phase.
- The CHANGELOG entry for the migration release lists every breaking change with a one-line migration note per item.
- Existing test files are renamed or updated to track the renames; no new test gaps are introduced. New tests added for: `getOr` on every container, `subscribe` on every container, `state()` / `peekState()` on `Derived` and `AsyncDerived`, sync `AsyncDerived.get()` + async `run()` / `runOr()`, `Symbol.dispose` on every disposable container, the four canonical traits, the new static aggregators.
- A migration script or codemod is not required, but a short "v0.3.x → v0.3.10 migration" note in `docs/guides/getting-started.md` (or its successor) lists the find-and-replace patterns for the renames.
- `aljabr/ui` and `aljabr/ui/dom` continue to work; any internal use of the renamed APIs is updated as part of this phase.

#### 5.12 — Constraints

- **No new abstractions in this phase.** Every change is reshaping existing surface to fit the style guide. New abstractions (`prose`, etc.) are gated behind v0.4.0 and will be designed against the post-migration surface.
- **One tagged release for all breaking changes.** Downstream consumers should migrate exactly once.
- **The style guide is the source of truth.** If implementation disagrees with the guide during this phase, the implementation is wrong.

### 6.0 Out of Scope (Tracked)

#### 5.1 — `Command` namespace / utility object

The grilling session considered shipping a `Command` namespace bundling `Command.protocol(...)` (a helper for building protocols), `Command.history(...)` (a history middleware factory), and miscellaneous helpers. This was rejected — the helpers either duplicate one-liners authors can write directly (`{ extract: identity, apply: myFn }`) or carry editor-flavoured concerns (history grouping rules, transaction batching) that don't belong in `prelude`. History lives inside `aljabr/ui/prose` (v0.4.1).

#### 5.2 — `union.intersect` / `union.difference`

See Phase 3.2. Skipped pending a concrete use case; both are typing puzzles with limited real-world demand.

#### 5.3 — Promotion of `parse.*` helpers to a generic `aljabr/parse` namespace

Considered briefly; the prose-flavoured parsers (`parse.jsx`, `parse.text`, `parse.html`, `parse.json`) are tightly coupled to the prose document schema and don't generalise. They land in `aljabr/ui/prose` in v0.4.0/0.4.2.

#### 5.4 — Generic history middleware in `prelude`

History as a reusable wrapper around `Dispatcher` was discussed for `prelude` but deferred. The behaviour authors actually want (debounce-grouped entries, transaction batching, `SetCursor`-style filters) is editor-flavoured. A non-editor consumer who needs "log every command, allow rollback" can write that wrapper in 30 lines using `RefArray<{ forward: Cmd, inverse: Cmd }>`. If a third domain emerges with the same exact wants, promote then.

### Design Constraints

- **No changes to the renderer surface.** `aljabr/ui`, `aljabr/ui/dom`, `aljabr/ui/canvas` are untouched in this release. The host system continues to work exactly as in v0.3.9.
- **`Signal` is unchanged.** Existing `Signal<T>` and `Signal<T, S>` consumers see no API or behaviour difference. `Dispatcher` is a sibling primitive.
- **No external dependencies introduced.** Implementation uses existing prelude primitives (`Validation`, the dependency-tracking machinery, `Scope` for disposal).
- **All existing tests pass without edits.** `test/prelude/`, `test/union.test.ts`, `test/match.test.ts` are unchanged. New tests are additive.

### Implementation Order

1. Phase 3: Union Algebra (no dependency on the new prelude primitives; lands first as a foundation).
2. Phase 4: `Schema.lazy` (independent of the prelude work; small addition to `aljabr/schema`. Land in parallel with Phase 3).
3. Phase 2: `CommandError` (small standalone union, depends only on existing `aljabr/schema`'s `DecodeError`).
4. Phase 1: `Dispatcher` (depends on `CommandError` for its `apply` return type).
5. Phase 5: API Consistency Migration. Lands last because every prior phase introduces new surface that must conform to the style guide before being baked in for v0.4.0. Sub-steps 1–5 of §5.10 are additive (compatible with the existing surface); sub-steps 6–11 are breaking and ship together in a single tagged release.

Phases 1–4 ship with full test coverage and documentation before the next begins. Phase 5 batches its breaking sub-steps but lands its additive sub-steps incrementally.

### Looking Forward

v0.4.0 lifts off from this foundation and begins the `aljabr/ui/prose` renderer. The first prose milestone uses `Dispatcher` as the document state, a domain-specific extension of `CommandError` for editor-specific failure modes, and `union.merge` as the author-extension mechanism for the prose command union. None of those connections are visible from v0.3.10's surface — but every line of v0.3.10 exists to make them clean.

Phase 5 ensures the surface every prose author meets in v0.4.0 is stable: one construction idiom per bucket, one read vocabulary across reactive containers, one verb for "read with default," one disposal idiom, one canonical set of traits. The cost is one disruptive release; the benefit is that the next year of additions sit on a normalized foundation rather than perpetuating drift.
