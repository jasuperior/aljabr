### **Aljabr Roadmap (v0.4.2): Prose Ergonomics**

**Strategic Vision**

After v0.4.1, prose is a working editor for the common case: contenteditable surface owned by the renderer, command-driven mutations, history with debounce-grouping, IME handling, plaintext + internal-clipboard paste, default keyboard bindings, native selection. Two related gaps remain: *getting documents into and out of the editor* (consumers need at least one of: load from plaintext, load from HTML, load from a wire-format JSON, save to a wire-format JSON), and *richer paste/drop ergonomics* (HTML paste, drag-and-drop, file uploads).

v0.4.2 closes both at once because they share an implementation. The full `parse` namespace ships — `parse.text`, `parse.html`, `parse.json` — and the same handlers map that powers `parse.html` populates the renderer's `paste.html` config slot. There is one source of truth for HTML → `ProseNode` mapping; authors who customize `parse.html` automatically customize HTML paste, and vice versa.

`documentSchema` is exported so authors using `aljabr/schema` elsewhere in their app can validate, encode, and decode document trees with the same primitive they use for API responses. The internal-clipboard encoding from v0.4.1's interim Codec is replaced with the Schema-driven path. Drag-and-drop and file-upload entry points round out the ergonomics.

The release is small relative to v0.4.0/0.4.1 — most of the architectural decisions are already made; v0.4.2 mostly *executes on them* by exporting the missing parsers and wiring the existing schemas through the missing surfaces. After v0.4.2, prose is production-ready for a wide swath of editor use cases. v0.5.0 then layers collaborative editing primitives on top.

### Phase 1: `parse.text`

#### 1.1 — Shape

```ts
import { parse } from "aljabr/ui/prose"

const result = parse.text("hello world\nsecond line\nhttps://example.com is a link")
// result: Validation<DocumentState, DecodeError>
//
// Valid value:
// <document>
//   <block><text>hello world</text></block>
//   <block><text>second line</text></block>
//   <block><text>is a link</text> with the URL as a <text link={{href:"https://example.com"}}>...</text></block>
// </document>
```

Returns `Validation<DocumentState, DecodeError>` like all other `parse.*` entries — uniform call-site shape.

#### 1.2 — Behaviour

- Newlines split into `<block>` elements (one per line).
- Empty lines produce empty `<block>` elements (preserves spacing intent).
- URLs matching a conservative pattern (`https?://[^\s]+`) auto-link, producing `<text link={{ href }}>...</text>`.
- All other text is plain `<text>` with no marks.

URL autodetection is tunable via an options argument:

```ts
parse.text(input, { autoLink: false })
parse.text(input, { autoLink: (text) => boolean })  // predicate to opt specific tokens in/out
```

#### 1.3 — Shared with the Paste Pipeline

The plaintext-splitter v0.4.1 ships under `paste.text` is the same function that powers `parse.text`. v0.4.2 lifts that function into the `parse` namespace and the renderer's `paste.text` slot defaults to it. Authors who customize one customize both — there is one source of truth for plaintext-to-document mapping.

#### 1.4 — Acceptance Criteria

- `parse.text("hello\nworld")` returns `Valid` carrying a `DocumentState` with two blocks.
- `parse.text("see https://example.com here")` produces a block with a linked text segment.
- Empty input produces a document with one empty block (the editor's cursor needs a block to live in).
- `autoLink: false` disables URL detection.
- The function powering `parse.text` is the same one used by `paste.text` in v0.4.1 (verified by reference equality in tests).
- A test file `test/ui/prose/parse-text.test.ts` covers each behaviour.

### Phase 2: `parse.html` and HTML Paste

#### 2.1 — Shape

```ts
import { parse } from "aljabr/ui/prose"

const result = parse.html(htmlString)
// result: Validation<DocumentState, DecodeError>
```

`parse.html` decodes through a `ParseHtmlHandlers` map — a record from lowercased HTML tag name to a function that produces `ProseNode` (or `ProseNode[]`, or `null` to drop):

```ts
type HtmlNodeDecoder = (el: Element) => ProseNode | ProseNode[] | null
type ParseHtmlHandlers = Record<string, HtmlNodeDecoder>
```

Authors override the default handlers by passing their own map:

```ts
parse.html(htmlString, myHandlers)
```

#### 2.2 — Why a `Validation` Return Type

HTML is wild. Pages from Word, Google Docs, Notion, Slack, etc. have idiosyncrasies that don't map cleanly to the prose primitive set. Returning `Validation<DocumentState, DecodeError>` makes parsing failures first-class rather than silently dropping content:

```tsx
const initial = match(parse.html(htmlString), {
    Valid:       ({ value })  => value,
    Invalid:     ({ errors }) => match(parse.text("(failed to parse)"), {
        Valid: ({ value }) => value,
        [__]:  () => { throw new Error("unreachable") },
    }),
    Unvalidated: ()           => match(parse.text(""), { Valid: ({ value }) => value, [__]: () => { throw new Error("unreachable") } }),
})
```

#### 2.3 — Default Handlers

`defaultParseHandlers.html` (exported from `aljabr/ui/prose`) handles:

- `<p>` → `<block>`
- `<h1>` through `<h6>` → `<heading level={N}>`
- `<blockquote>` → `<quote>`
- `<pre>`, `<pre><code>` → `<code>`
- `<strong>`, `<b>` → `text bold`
- `<em>`, `<i>` → `text italic`
- `<u>` → `text underline`
- `<s>`, `<del>` → `text strike`
- `<code>` (inline) → `text code`
- `<a href>` → `text link={{ href }}`
- `<img src alt>` → `<image>`
- `<hr>` → `<hr>`
- Inline styles (e.g., Word's `<span style="font-weight:700">`) → recognized for built-in marks where possible, dropped otherwise
- Unknown elements → flatten to text content

Authors compose with plain object spreading:

```ts
import { defaultParseHandlers, ProseNode } from "aljabr/ui/prose"

const myHandlers = {
    ...defaultParseHandlers.html,
    details: (el) => ProseNode.Block(/* author-supplied conversion */),
}

parse.html(htmlString, myHandlers)
```

#### 2.4 — HTML Paste Lights Up

The renderer's `paste.html` config slot — declared but unused in v0.4.1 — accepts the same `ParseHtmlHandlers` shape and defaults to `defaultParseHandlers.html`. Authors who customize `parse.html` typically pass the same handlers map to `paste.html`:

```ts
const myHtmlHandlers = { ...defaultParseHandlers.html, details: detailsDecoder }

const { view, mount } = ProseRenderer.create(root, {
    paste: { html: myHtmlHandlers },
})

// And separately:
const initialFromHtml = parse.html(someHtml, myHtmlHandlers)
```

There is **one** source of truth for HTML → `ProseNode` mapping. Authors who only use one path (parse-on-load *or* paste, not both) just don't pass the handlers to the other; the default applies.

The `onPaste` event's `source` field gains the `"html"` value in v0.4.2:

```tsx
<document state={doc} onPaste={(e) => {
    if (e.source === "html") { /* lit up in v0.4.2 */ }
}} />
```

#### 2.5 — Acceptance Criteria

- `parse.html("<p>hello</p>")` returns `Valid` carrying a single-block document.
- `parse.html` with a custom handlers map produces output matching the handlers.
- A malformed input that the handlers reject produces `Invalid` with structured errors.
- The renderer's `paste.html` slot accepts the same shape as `parse.html`'s handlers argument and defaults to `defaultParseHandlers.html`.
- HTML paste produces an `onPaste` event with `source: "html"` and dispatches splice commands matching the parsed `ProseNode[]`.
- A test file `test/ui/prose/parse-html.test.ts` and additions to `test/ui/prose/paste.test.ts` cover both paths sharing one handlers map.

### Phase 3: `documentSchema` and `parse.json`

#### 3.1 — `documentSchema`

A complete `Schema<DocumentState>` definition for the prose document tree, exported from `aljabr/ui/prose`. Authors use it for:

- Validating wire-format API payloads before seeding an editor (`decode(documentSchema, json)`).
- Encoding documents for sending across the wire (`encode(documentSchema, doc)`).
- Round-trip testing of documents under transformations.

```ts
import { documentSchema } from "aljabr/ui/prose"
import { encode, decode } from "aljabr/schema"

const json = encode(documentSchema, doc.peekState())
// transmit json over the wire

const incoming = decode(documentSchema, jsonFromApi)
// incoming: Validation<DocumentState, DecodeError>
```

`encode` and `decode` are the existing free functions from `aljabr/schema`. `documentSchema` is just a value of type `Schema<DocumentState>`.

#### 3.2 — Schema Shape

`documentSchema` is built with `Schema.object`, `Schema.variant`, `Schema.array`, and the new `Schema.lazy` from v0.3.10 (required because `<document>` contains `ProseNode` children, which contain more `ProseNode` children — recursive). The `marks` field on the `<text>` variant is `Schema.array(Schema.variant(MarkSet, {...}))` — a typed list of mark variants, matching the v0.4.0 design where `marks` is `MarkSet[]`.

```ts
import { Schema } from "aljabr/schema"
import { ProseNode, MarkSet } from "aljabr/ui/prose"

const markSetSchema = Schema.variant(MarkSet, {
    Mention: Schema.object({ userId: Schema.string() }),
    Comment: Schema.object({ threadId: Schema.string() }),
    // ...one entry per built-in MarkSet variant
})

const proseNodeSchema: Schema<ProseNode> = Schema.variant(ProseNode, {
    Document:  Schema.object({ children: Schema.array(Schema.lazy(() => proseNodeSchema)) }),
    Block:     Schema.object({ children: Schema.array(Schema.lazy(() => proseNodeSchema)) }),
    Heading:   Schema.object({ level: Schema.number(), children: Schema.array(Schema.lazy(() => proseNodeSchema)) }),
    Quote:     Schema.object({ children: Schema.array(Schema.lazy(() => proseNodeSchema)) }),
    Code:      Schema.object({ language: Schema.nullable(Schema.string()), children: Schema.array(Schema.lazy(() => proseNodeSchema)) }),
    Text:      Schema.object({ content: Schema.string(), marks: Schema.array(markSetSchema) }),
    Image:     Schema.object({ src: Schema.string(), alt: Schema.nullable(Schema.string()), caption: Schema.nullable(Schema.string()) }),
    HardBreak: Schema.object({}),
    Hr:        Schema.object({}),
})

export const documentSchema: Schema<DocumentState> = Schema.object({
    doc:       proseNodeSchema,
    cursor:    editorRangeSchema,
    composing: Schema.boolean(),
})
```

#### 3.3 — Extending `documentSchema`

There is no `Schema.merge` (it does not exist on `Schema`, which is a factory namespace, not a union). Extension happens at the *union* layer, then the schema is rebuilt:

```ts
import { Schema } from "aljabr/schema"
import { MarkSet, ProseNode, editorRangeSchema } from "aljabr/ui/prose"

// 1. Extend MarkSet via union algebra (v0.3.10).
const MyMarkSet = MarkSet.merge({
    Mention: (userId: string) => ({ userId }),
})

// 2. Rebuild the mark schema with the extended union.
const myMarkSetSchema = Schema.variant(MyMarkSet, {
    // ...existing variants from MarkSet
    Mention: Schema.object({ userId: Schema.string() }),
})

// 3. Rebuild proseNodeSchema and documentSchema using the extended mark schema.
//    (The full body is the same as Phase 3.2 with `markSetSchema` swapped for `myMarkSetSchema`.)
```

The `documentSchema` exported from `aljabr/ui/prose` is a *value* — an expression authors can read for reference and rebuild against extended unions. There is no `buildDocumentSchema(...)` helper; the rebuild is ~20 lines of declarative Schema expression that authors copy and adapt. If demand emerges later for a parameterized helper, it can be added without breaking the value-based default.

#### 3.4 — `parse.json`

A thin ergonomic wrapper around `decode(documentSchema, ...)`:

```ts
parse.json(jsonValue)
// equivalent to: decode(documentSchema, jsonValue)
// returns: Validation<DocumentState, DecodeError>

parse.json(jsonValue, mySchema)
// uses a custom Schema<DocumentState> instead of documentSchema
```

Authors who already use `aljabr/schema` elsewhere in their app can reach for `decode` directly; authors who don't want to think about schema use `parse.json`. Both paths produce the same `Validation<DocumentState, DecodeError>`.

#### 3.5 — Acceptance Criteria

- `documentSchema` round-trips a non-trivial document via the `roundtrip` utility from `aljabr/schema`.
- `decode(documentSchema, validJson)` returns `Valid(state)` matching the input.
- `decode(documentSchema, invalidJson)` returns `Invalid(errors)` with structured errors pointing at the failure path.
- A custom `Schema<DocumentState>` built against an extended `MarkSet` decodes documents containing those custom marks (verified by hand-rolled example following the §3.3 pattern).
- `parse.json(json)` is functionally identical to `decode(documentSchema, json)`.
- A test file `test/ui/prose/document-schema.test.ts` covers round-trip, partial-validity error reporting, and the manual extension pattern.

### Phase 4: Internal Clipboard via `documentSchema`

#### 4.1 — Replace the Interim Codec

v0.4.1's internal clipboard uses a hand-coded `Codec<unknown, DocumentState>` for `application/x-aljabr-doc+json`. v0.4.2 replaces both halves with the Schema-driven path:

- **Copy:** `encode(documentSchema, fragmentState)` produces the JSON for the clipboard.
- **Paste:** `decode(documentSchema, clipboardJson)` produces the `DocumentState` to insert.

#### 4.2 — Why This Matters

Round-trip is provable via the `roundtrip` utility from `aljabr/schema`. Internal copy/paste of any document — including custom marks an author has added via union extension — produces an identical document tree. Without the Schema-driven path, custom marks would silently drop on internal paste.

#### 4.3 — Author-Extended Document Schemas

The internal-clipboard pipeline reads the Schema from the renderer's config:

```ts
const { view, mount } = ProseRenderer.create(root, {
    paste: { internal: myDocumentSchema },
})
```

Authors with extended document schemas (custom marks, custom node attributes — built following the §3.3 pattern) pass the extended Schema. The default uses `documentSchema` — most authors do not configure this.

#### 4.4 — Acceptance Criteria

- Internal copy/paste round-trips a document with built-in marks via the Schema.
- Internal copy/paste round-trips a document with author-extended marks when the extended Schema is configured.
- v0.4.1's interim Codec is removed; no consumer of the renderer relies on it externally.
- The existing internal-clipboard tests from v0.4.1 continue to pass with the new Schema-driven path.

### Phase 5: Drag-and-Drop and File Uploads

#### 5.1 — `onDrop` Synthetic Event

A new synthetic event on `<document>`:

```tsx
<document
    state={doc}
    onDrop={({ files, html, text, range }) => {
        // file drag-and-drop, internal drag-and-drop, or HTML/text drop from another app
    }}
/>
```

Payload:

| Field | Description |
|---|---|
| `files` | `File[]` — files dropped on the editor |
| `html` | `string \| null` — HTML payload from the drag operation |
| `text` | `string \| null` — plaintext payload |
| `range` | `EditorRange` — where in the document the drop landed |

The handler is invoked once per drop. If the handler returns nothing, the renderer falls back to the default behaviour: `html` flows through `paste.html` Schema; `text` flows through `paste.text`; files are ignored (uploads are author-domain).

#### 5.2 — `drop.files` Config

The default file-handling behaviour (ignore) can be replaced via a config slot — the same shape as `paste.files`:

```ts
const { view, mount } = ProseRenderer.create(root, {
    paste: { files: ({ files, range }) => uploadAndInsert(files, range) },
    drop:  { files: ({ files, range }) => uploadAndInsert(files, range) },
})
```

A common shorthand collapses the two:

```ts
const fileHandler = ({ files, range }) => uploadAndInsert(files, range)
const { view, mount } = ProseRenderer.create(root, {
    paste: { files: fileHandler },
    drop:  { files: fileHandler },
})
```

#### 5.3 — Internal Drag-and-Drop

Dragging selected content from one position in the document to another is handled by the renderer:

- On `dragstart` over a selection, the renderer serializes the selected fragment using the internal-clipboard encoding from Phase 4.
- On `drop`, if the source was the same renderer, the renderer dispatches a transaction that deletes the source range and inserts the fragment at the drop range.
- `onDrop` is not fired for internal drag-and-drop — the operation is invisible to authors.

Cross-document internal drag-and-drop (between two `<document>` elements bound to different signals) is supported via the same internal-clipboard encoding.

#### 5.4 — Acceptance Criteria

- `onDrop` fires with the documented payload for external drops.
- `drop.files` is invoked for file drops when configured.
- Internal drag-and-drop within a single document moves content as a transaction (one undo entry).
- Internal drag-and-drop between two `<document>` elements (same `ProseRenderer.create` instance) moves content correctly.
- A test file `test/ui/prose/drag-and-drop.test.ts` covers each path.

### Phase 6: Custom Mark Render Overrides

#### 6.1 — Renderer Map for `MarkSet` Variants

Custom marks (variants of `MarkSet` added via `MarkSet.merge`) default to `data-*` attributes derived from the variant tag and payload keys. Authors override the DOM rendering by passing a `markRenderers` map to the renderer config:

```tsx
import { ProseRenderer } from "aljabr/ui/prose"

const { view, mount } = ProseRenderer.create(root, {
    markRenderers: {
        Mention: ({ payload, children }) => (
            <a class="mention" href={`/u/${payload.userId}`}>{children}</a>
        ),
    },
})
```

`markRenderers` is `Record<string, (args: { payload: object; children: ViewNode }) => ViewNode>`, keyed by the variant tag name. The renderer dispatches per-mark by tag and falls back to the `data-*` default when no entry exists. Authors do not need to declare a renderer for every variant — only the ones they want to customize.

This shape keeps render functions out of the data model. A `MarkSet.Mention({ userId })` value is plain data; the rendering policy lives in renderer config alongside other DOM-mapping concerns. This matches how the rest of `aljabr/ui` separates data from view logic.

#### 6.2 — When to Use This

This is an escape hatch for cases where the default `data-*` attribute approach is insufficient — e.g., interactive marks (mentions that need a hover popover, comments that need a reply UI). For most custom marks, the default rendering is fine and the author styles via CSS targeting `data-mention-user-id` etc.

#### 6.3 — Acceptance Criteria

- A custom `MarkSet` variant with an entry in `markRenderers` renders the author's element wrapping the marked text.
- A custom variant without an entry falls back to `data-*` attribute stamping.
- Updating `markRenderers` between mounts produces the expected DOM (re-mounts pick up the change; existing mounts are not retroactively updated).
- A test file `test/ui/prose/custom-mark-render.test.ts`.

### 7.0 Out of Scope (Tracked)

#### 7.1 — `<remoteSelection>` overlay primitive

Deferred to v0.5.0. The infrastructure for collaborative cursors — overlay rendering on top of the native selection, presence-protocol agnostic shape — needs its own design pass.

#### 7.2 — Custom-drawn selection (multi-cursor, persistent across blur)

Deferred to v0.5.0. Reimplementing word-boundary navigation, IME caret positioning, and OS-specific keyboard semantics is enormous and not justified for the v0.4.x cycle.

#### 7.3 — Branching history

Deferred. Considered during the prose-design grilling and parked pending real-consumer demand.

#### 7.4 — Plugin / package convention

If demand emerges for third-party prose extensions, a thin convention (a "prose plugin" is a function returning a partial command-set + apply override + bindings + a `ParseHtmlHandlers` fragment) can be documented without changing the core surface. v0.4.x does not promote this convention preemptively — authors who extend already have all the primitives they need (`ProseCommand.merge`, `MarkSet.merge`, `match()`-with-`[__]`, plain object spreading for handler maps).

#### 7.5 — Operational transformation / CRDT integration

Collaborative editing semantics are v0.5.0+ work. The command-driven foundation in v0.3.10 plus the Schema-encoded transport in v0.4.2 are prerequisites. The actual transform / merge logic ships when concrete collaboration use cases drive the design.

### Design Constraints

- **Additive surface only.** v0.4.2 fills in `parse.text`, `parse.html`, `parse.json`; lights up the `paste.html` config slot declared in v0.4.1; exports `documentSchema` and `defaultParseHandlers`; adds `onDrop` and `drop` config; adds the `markRenderers` config slot. Existing surfaces (`Dispatcher`, `History.create`, `ProseRenderer.create`, `<document>`, `parse.jsx`, `proseProtocol`, the `bindings` prop) are unchanged.
- **One source of truth for HTML mapping.** `parse.html` and the renderer's `paste.html` share the same `ParseHtmlHandlers` shape. Authors who customize one path can pass the same handlers map to the other; there is no separate "paste schema" vs. "parse schema."
- **Schema integration where the type fits.** Internal-clipboard JSON and wire-format JSON go through `Schema<DocumentState>` (`documentSchema`). HTML and plaintext do not — they use plain decoder functions because their input is a DOM `Element` / string and there is no encode side.
- **`Schema.merge` is not used and not added.** Extension of `documentSchema` happens at the union layer (`MarkSet.merge`, `ProseNode.merge`) followed by a manual schema rebuild — ~20 lines of declarative Schema expression authors copy from §3.2.
- **No external dependencies introduced.** Implementation uses existing prelude/schema primitives and browser APIs (DOMParser, drag/drop events).
- **All v0.4.0/0.4.1 tests pass without edits.** v0.4.2 features are additive.

---

### Implementation Order

1. Phase 3: `documentSchema` + `parse.json` (depends on `Schema.lazy` from v0.3.10; foundation for Phases 4 and 5).
2. Phase 4: Internal Clipboard via `documentSchema` (replaces v0.4.1's interim Codec; depends on Phase 3).
3. Phase 1: `parse.text` (independent; small; lifts the v0.4.1 plaintext paste handler into the namespace).
4. Phase 2: `parse.html` and HTML Paste (independent of Phases 1, 3, 4; can ship in parallel).
5. Phase 5: Drag-and-Drop (depends on Phase 4 for internal-drag serialization and Phase 2 for HTML drop).
6. Phase 6: Custom Mark Render Overrides (independent; small).

Each phase ships with full test coverage and documentation before the next begins.

---

### Looking Forward

After v0.4.2, prose has all the foundations a single-user editor needs: model-owned DOM, command-driven history, IME, paste, bindings, parsing in/out, drag-and-drop, custom marks. Authors can ship production text-editor experiences on top of `aljabr/ui/prose` with no third-party dependencies.

v0.5.0 begins the collaborative-editing chapter: the `<remoteSelection>` overlay primitive, custom-drawn selection rendering for multi-cursor support, and the operational-transform or CRDT integration that makes real-time collaboration possible. The schema-encoded wire format from v0.4.2 is the transport substrate that work will build on.

Branching history, plugin conventions, and accessibility deep-dives are tracked for when consumer demand makes them concrete. The prose design intentionally ships *small primitives that compose* rather than *large frameworks with many opinions*; if a future feature stays out of the codebase because no real consumer needs it yet, that is the design working.
