### **Aljabr Roadmap (v0.4.1): Prose Extensions**

**Strategic Vision**

v0.4.0 lands the prose foundation: a renderer that owns its DOM, a closed primitive set, a typed command union, native selection binding, and read-only support. Authors can mount a document, dispatch commands, and observe selection changes — but the editor is missing the four features that make a contenteditable surface *usable*: history, IME composition handling, paste sanitization, and default keyboard bindings.

v0.4.1 lands all four. They build on `<document>`'s prop surface (new event callbacks, new `bindings` prop, new `paste` config), on the v0.3.10 `Dispatcher` machinery (validated transactional updates, inverses produced inline by `apply`), and — only where the type genuinely fits — on `aljabr/schema`. The release is large in scope but coherent: each feature plugs into the existing extension points without rearchitecting anything.

After this release, prose is functionally a working editor for the common case. v0.4.2 layers richer parsers and Schema-driven extensibility on top; v0.5.0 adds collaborative-editing primitives.

### Phase 1: History

#### 1.1 — Shape

`History` wraps a `Dispatcher` and intercepts every `dispatch` to record `(forward, inverse)` pairs into a debounce-grouped log. The wrapper does **not** re-export the dispatcher's full surface — authors keep dispatching through the original `doc` reference. Undo and redo are themselves `ProseCommand` variants, so the bindings handler invokes them via `doc.dispatch(...)` like any other command.

```ts
import { Dispatcher } from "aljabr"
import { History, ProseCommand, defaultGrouping } from "aljabr/ui/prose"

const doc = Dispatcher.create(initial, proseProtocol)
const history = History.create(doc, {
    limit: 100,
    grouping: defaultGrouping,           // see Phase 1.2
})

doc.dispatch(ProseCommand.Insert("a", point))   // recorded
doc.dispatch(ProseCommand.Undo())               // pops the entry, dispatches its inverses
doc.dispatch(ProseCommand.Redo())               // re-applies them

history.canUndo                                  // Signal<boolean>
history.canRedo                                  // Signal<boolean>
history.entries                                  // Signal<readonly HistoryEntry[]>  — see Phase 1.6
history.transaction(() => {
    doc.dispatch(ProseCommand.Format("bold", range))
    doc.dispatch(ProseCommand.Insert("hi", point))
})                                               // collapses into one entry regardless of grouping
```

`HistoryEntry`:

```ts
type HistoryEntry = {
    groupKey: string | null
    timestamp: number
    commands: { forward: ProseCommand, inverse: ProseCommand }[]
}
```

#### 1.2 — Grouping Registry on `History.create`

Grouping rules live on the `History` middleware, not on individual command payloads. The `grouping` option is a record keyed by variant tag name; each entry declares the group key and debounce window for that variant. Variants absent from the record are recorded as ungrouped (one entry each); variants whose entry has `omit: true` are filtered out of history entirely (the typical case for `SetCursor`).

```ts
type GroupingRule =
    | { key: string; window: number }   // debounce-grouped under shared key
    | { omit: true }                    // never recorded

type GroupingMap = Record<string, GroupingRule>

export const defaultGrouping: GroupingMap = {
    Insert:         { key: "insert", window: 500 },
    DeleteBackward: { key: "delete", window: 500 },
    DeleteForward:  { key: "delete", window: 500 },
    SetCursor:      { omit: true },
    // Format, SplitBlock, MergeBlock, SetBlockKind absent → recorded ungrouped
    // Undo/Redo absent → recorded ungrouped, but the middleware short-circuits them (see Phase 1.5)
}
```

**Why a registry instead of payload-carried metadata:** an earlier draft of this roadmap had every command variant carry `groupKey` and `groupWindow` on its payload. That made grouping rules *viral* — every author-defined extension command had to decide on grouping fields whether they cared or not, and changing the default window required rebuilding the union. The registry decouples the rule from the variant. Authors who add custom commands and want them to collapse with built-in inserts pass `{ ...defaultGrouping, MyInsert: { key: "insert", window: 500 } }`. Authors who never customize grouping pass `defaultGrouping` and never think about it.

The tradeoff: collapsing rules are not part of the command's identity, so a command crossing a serialization boundary loses its grouping intent unless the receiver shares the same registry. Prose v0.4.1 has no such boundary (history is local and in-memory), so the registry wins on ergonomics with no current downside. If collaborative-editing transports in v0.5.0 ever need per-command grouping intent, the rule can move onto the payload at that time without breaking the registry path (the registry would just become a default that the payload overrides).

#### 1.3 — Debounce Grouping Logic

The middleware looks up the rule for the dispatched command's tag, then either skips, appends to the current entry, or starts a new entry:

```ts
function recordCommand(
    entries: RefArray<HistoryEntry>,
    grouping: GroupingMap,
    cmd: ProseCommand,
    inverse: ProseCommand,
    now: number,
): void {
    const rule = grouping[cmd[tag]]
    if (rule && "omit" in rule) return

    const last = entries.peek().at(-1)
    const canCollapse =
        last !== undefined &&
        rule !== undefined &&
        "key" in rule &&
        rule.key === last.groupKey &&
        now - last.timestamp <= rule.window

    if (canCollapse) {
        last.commands.push({ forward: cmd, inverse })
        last.timestamp = now
    } else {
        entries.push({
            groupKey: rule && "key" in rule ? rule.key : null,
            timestamp: now,
            commands: [{ forward: cmd, inverse }],
        })
    }
}
```

#### 1.4 — `Undo` / `Redo` as `ProseCommand` variants

The `ProseCommand` union from v0.4.0 gains two variants in v0.4.1:

```ts
export const ProseCommand = union({
    // ... existing variants from v0.4.0
    Undo: () => ({}),
    Redo: () => ({}),
})
```

`defaultApply` does **not** handle `Undo` / `Redo` — the `History` middleware intercepts them before they reach `apply`. (If `History` is not wrapping the dispatcher, dispatching `Undo` falls through to `defaultApply`'s `[__]` arm and is a no-op or `Validation.Invalid`, depending on the author's composition.)

This shape means:

- Bindings handlers (`Mod-z`, `Mod-Shift-z`) just call `doc.dispatch(ProseCommand.Undo())`. They don't need a reference to the `History` instance.
- Programmatic undo from anywhere in the app uses the same channel.
- Authors who want to inspect *which* command produced an undo can `match()` on `ProseCommand` arms in their own command-stream listeners (a v0.4.x ergonomic; not core to the surface).

#### 1.5 — Middleware Interception

`History.create` builds a wrapped `Dispatcher` whose `dispatch` is replaced. The replacement runs *before* the underlying `apply`:

```ts
function wrappedDispatch(cmd: ProseCommand): Validation<...> {
    return match(cmd, {
        Undo: () => {
            const entry = entries.peek().at(-1)
            if (!entry) return Validation.Valid({ next: doc.peekState(), inverse: cmd })
            for (const { inverse } of [...entry.commands].reverse()) {
                originalDispatch(inverse)   // dispatches without re-recording
            }
            entries.pop()
            redoStack.push(entry)
            return Validation.Valid({ next: doc.peekState(), inverse: ProseCommand.Redo() })
        },
        Redo: () => {
            const entry = redoStack.peek().at(-1)
            if (!entry) return Validation.Valid({ next: doc.peekState(), inverse: cmd })
            for (const { forward } of entry.commands) {
                originalDispatch(forward)
            }
            redoStack.pop()
            entries.push(entry)
            return Validation.Valid({ next: doc.peekState(), inverse: ProseCommand.Undo() })
        },
        [__]: (other) => {
            const result = originalDispatch(other)
            match(result, {
                Valid: ({ value: { inverse } }) => recordCommand(entries, grouping, other, inverse, Date.now()),
                Invalid: () => { /* nothing to record */ },
                Unvalidated: () => {},
            })
            // A new non-undo dispatch clears the redo stack — standard editor behaviour.
            redoStack.clear()
            return result
        },
    })
}
```

The wrapper preserves the `Dispatcher` type so `<document state={doc}>` still works. The `originalDispatch` reference is captured in a closure so undo/redo can re-dispatch inverses without re-recording.

#### 1.6 — `History`'s Read Surface

The `History` instance exposes its own reactive surface, separate from the `Dispatcher`'s state. Authors who need to inspect the stack lexically capture `history` alongside `doc`:

```ts
type History = {
    canUndo: Signal<boolean>
    canRedo: Signal<boolean>
    entries: Signal<readonly HistoryEntry[]>   // wraps an internal RefArray; the public read is a tracked snapshot
    transaction(fn: () => void): void
}
```

`entries` is a `Signal<readonly HistoryEntry[]>` — a tracked read of the underlying log. The internal storage is a `RefArray<HistoryEntry>`; the public Signal is derived from it (`Derived.from(entries)`). This avoids handing authors a writable `RefArray` they could mutate behind the middleware's back, and it gives them the standard `Signal` read API they already know.

#### 1.7 — `transaction(fn)`

Inside `transaction`, all dispatched commands collapse into one entry regardless of grouping. Implementation: the middleware sets a transaction flag; while set, `recordCommand` accumulates into a single in-progress entry instead of consulting `grouping`. The flag is cleared in a `finally` block so a thrown handler still closes the entry cleanly.

```ts
history.transaction(() => {
    doc.dispatch(ProseCommand.Format("bold", range))
    doc.dispatch(ProseCommand.Insert("hi", point))
    doc.dispatch(ProseCommand.Format("italic", range))
})
// doc.dispatch(ProseCommand.Undo()) pops one entry, applies all three inverses in reverse order
```

#### 1.8 — Acceptance Criteria

- `History.create(doc, { limit, grouping })` returns a wrapper that intercepts `dispatch` on `doc`. `doc.dispatch(...)` continues to work; `Undo`/`Redo` variants are short-circuited by the middleware, all other commands flow through the original `apply` and are recorded.
- Two consecutive `Insert` dispatches within the `Insert` rule's `window` collapse into one history entry.
- Two consecutive `Insert` dispatches outside the window are separate entries.
- `Format` dispatches (no grouping rule) are always separate entries.
- `SetCursor` dispatches (rule = `{ omit: true }`) are not recorded.
- `transaction(fn)` collapses all dispatches inside `fn` into a single entry; a thrown handler still closes the entry.
- `doc.dispatch(ProseCommand.Undo())` and `doc.dispatch(ProseCommand.Redo())` round-trip the document state.
- A new dispatch after one or more undos clears the redo stack.
- Reaching `limit` drops the oldest entry from the head of the internal `RefArray`.
- `history.canUndo`, `history.canRedo`, and `history.entries` are tracked Signals that update on every recorded change.
- Custom commands grouped under an existing key (`{ ...defaultGrouping, MyInsert: { key: "insert", window: 500 } }`) collapse with built-in inserts.
- A new test file `test/ui/prose/history.test.ts` covers all of the above.
- Documentation in `docs/api/prose/history.md`.

### Phase 2: IME Composition

#### 2.1 — The Hybrid Model

During IME composition (CJK input, dead keys, emoji pickers, autocorrect on iOS, voice dictation), the browser **must** write to the DOM — IMEs need a live preview to render candidate characters and let the user navigate them. The renderer cannot prevent default on `compositionupdate` without breaking IME on most platforms.

The hybrid model:

- **Visual surface yields to the browser.** Between `compositionstart` and `compositionend`, the renderer stops being authoritative for the contenteditable region. The browser writes its preview into the DOM.
- **Model yields too.** No content-mutating commands are dispatched during composition. The `Dispatcher`'s `doc` field (the document tree) is unchanged from `compositionstart` until commit.
- **Composing state lives on `DocumentState`.** A single `composing: boolean` field on `DocumentState` is flipped to `true` on `compositionstart` and back to `false` on `compositionend`/cancel — via internal commands the renderer dispatches (`SetComposing(true)` / `SetComposing(false)`, added to `ProseCommand` in v0.4.1). Authors read it via `doc.state().composing` like any other state field; no controller-like side channel is needed. This keeps the "no separate controller object" promise from v0.4.0 intact.
- **Authors get a live event stream.** `onCompose` fires at every phase with the partial text, so features like "@-mention autocomplete during composition" work without affecting the surface.

#### 2.2 — Phase Behaviour

| Phase | Renderer behaviour | Author signal |
|---|---|---|
| `compositionstart` | Dispatch `SetComposing(true)` (flips `doc.state().composing`). Disable content-mutating command dispatch (except `SetComposing(false)`). | `onCompose({ phase: "start" })` |
| `compositionupdate` | Do nothing to DOM; let browser draw preview. | `onCompose({ phase: "update", text })` |
| `compositionend` | Read final text from the DOM; dispatch `ProseCommand.Insert(text, at)`; revert any partial DOM mutations not represented by the final command; dispatch `SetComposing(false)`. | `onCompose({ phase: "end", text })` |
| User cancels (Esc) | Dispatch nothing into the document tree; renderer reverts DOM to pre-composition state. Dispatch `SetComposing(false)`. | `onCompose({ phase: "cancel" })` |

The `SetComposing` command is also added to `defaultGrouping` with `{ omit: true }` — it is never recorded in history.

#### 2.3 — Why the Hybrid (Not Pure Yield, Not Pure Mirror)

- **Pure yield** (yield visual + yield model + no live events) is the safest baseline — ProseMirror's strategy. It works but leaves authors blind during composition, killing features like live autocomplete (a real-world need: typing "@jam" should show mention candidates *during* the IME composition, not only after the user commits).
- **Pure mirror** (rewrite the DOM on every `compositionupdate`) fights the browser and loses on Android Chrome and macOS Safari specifically — the candidate window misaligns and IME hangs.
- **Hybrid** threads it: model yields (no commits during composition, no DOM rewrites), authors get an event stream they can subscribe to.

#### 2.4 — Acceptance Criteria

- `compositionstart` dispatches `SetComposing(true)`; `doc.state().composing` reads `true` thereafter.
- `compositionupdate` fires `onCompose` with the partial text but does not dispatch into the document tree.
- `compositionend` dispatches a single `Insert` command with the final text, then `SetComposing(false)`.
- Esc during composition dispatches `SetComposing(false)` only; the document tree is unchanged.
- `SetComposing` commands are not recorded in history.
- A test file `test/ui/prose/ime.test.ts` covers each phase and the cancel path. Tests use synthesized composition events because JSDOM does not natively fire them — the test harness includes a small composition-event simulator.

### Phase 3: Paste Sanitization

#### 3.1 — Paste Wires Into `parse`

Paste is not a separate domain. Browser paste events feed into the `parse` namespace (v0.4.2), which produces `Validation<DocumentState, DecodeError>` from any of four input formats. Paste differs from `parse` only in *where the result goes*: instead of seeding a fresh document, the parsed `doc.children` are spliced into the existing document at the cursor.

This means the bulk of the paste-pipeline configuration — HTML tag handlers, plaintext splitter, JSON schema — lives in v0.4.2 alongside the `parse` namespace. v0.4.1 ships only what the renderer needs to *wire* paste events:

- The browser `paste` event listener.
- The `<onPaste>` synthetic event (Phase 5 of v0.4.0 already declared this slot).
- A plaintext path (newline → block, URL autolink).
- An interim internal-clipboard `Codec<unknown, DocumentState>` for `application/x-aljabr-doc+json` (v0.4.2 lifts this onto the real `documentSchema`).
- A `paste.files` config slot (no-op default).

**HTML paste is deferred to v0.4.2**, where it lights up alongside `parse.html`. v0.4.1 pasting from an HTML-aware app falls back to plaintext (the clipboard's `text/plain` payload).

#### 3.2 — `paste` Config

```ts
type ParseHandlers = {
    text?:     (text: string) => ProseNode[]      // plaintext splitter; default in Phase 3.3
    internal?: Schema<DocumentState>              // interim Codec in v0.4.1; documentSchema in v0.4.2
    files?:    (args: { files: File[]; range: EditorRange }) => void
    // html?: ParseHtmlHandlers                    // ships in v0.4.2
}

const { view, mount } = ProseRenderer.create(root, { paste: myHandlers })
```

The shape is forward-compatible: when v0.4.2 adds `html?:` to `ParseHandlers`, existing v0.4.1 configurations keep working unchanged.

#### 3.3 — Default Plaintext Behaviour

Newline-delimited blocks; URL pattern (`https?://[^\s]+`) auto-links. Identical to `parse.text` (v0.4.2). A single shared implementation lives in `aljabr/ui/prose` and is reused both as the plaintext paste handler and as `parse.text`.

#### 3.4 — Internal Clipboard

Copy serializes a `DocumentState` fragment to `application/x-aljabr-doc+json` (using an interim hand-coded `Codec<unknown, DocumentState>` in v0.4.1, swapped for the real `documentSchema` in v0.4.2). Paste of `application/x-aljabr-doc+json` decodes via the same Codec.

The `onPaste` event's `source` field distinguishes pastes:

```ts
<document state={doc} onPaste={(e) => {
    if (e.source === "internal") { /* came from this or another aljabr/ui/prose editor */ }
    if (e.source === "text")     { /* plaintext */ }
    // e.source === "html" appears in v0.4.2
}} />
```

#### 3.5 — Acceptance Criteria

- The renderer wires the browser `paste` event into the configured `paste` handlers and dispatches the parsed result as commands at the cursor (one transactional history entry).
- Pasting plaintext with newlines splits into blocks; URLs auto-link.
- Internal copy/paste round-trips via the interim `Codec<unknown, DocumentState>`.
- The `paste.files` handler fires for file pastes when configured; the default no-op is invoked otherwise.
- An HTML clipboard payload falls back to its `text/plain` companion (browser provides both); `e.source === "text"` in `onPaste`.
- A test file `test/ui/prose/paste.test.ts` covers each surface and the internal round-trip.
- Documentation in `docs/api/prose/paste.md` notes that HTML paste lights up in v0.4.2.

### Phase 4: Default Keyboard Bindings

#### 4.1 — Static Map on `<document>`

```tsx
import { defaultBindings, ProseCommand } from "aljabr/ui/prose"

<document
    state={doc}
    bindings={{
        ...defaultBindings,
        "Mod-b": (doc) => doc.dispatch(ProseCommand.Format("bold", doc.state().cursor)),
    }}
/>
```

`bindings` is a `Record<string, (doc: Dispatcher<DocumentNode, DocumentState, ProseCommand>) => void>` where the key is a key-binding descriptor (e.g., `"Mod-b"`, `"Enter"`, `"Shift-Enter"`, `"Mod-z"`). The `Mod` token resolves to `Cmd` on macOS and `Ctrl` elsewhere — standard cross-platform editor convention.

The handler receives the same `Dispatcher` instance the author already owns. There is **no** separate `ProseController` object. Authors who need to inspect the history stack from a binding handler lexically capture the `History` instance alongside `doc`:

```tsx
const doc = Dispatcher.create(initial, proseProtocol)
const history = History.create(doc, { limit: 100, grouping: defaultGrouping })

<document
    state={doc}
    bindings={{
        ...defaultBindings,
        "Mod-Shift-h": () => console.log(history.entries.get()),
    }}
/>
```

Undo and redo, being `ProseCommand` variants, do not need access to `history` from the handler at all — `Mod-z` just dispatches `ProseCommand.Undo()` through `doc`.

#### 4.2 — `defaultBindings`

| Key | Action |
|---|---|
| `Enter` | `dispatch(SplitBlock(cursor))` |
| `Shift-Enter` | `dispatch(Insert("\n", cursor))` (hard break inside a block) |
| `Backspace` | `dispatch(DeleteBackward(currentRange))` (single character if collapsed; the range if extended) |
| `Delete` | `dispatch(DeleteForward(currentRange))` |
| `Mod-z` | `dispatch(Undo())` |
| `Mod-Shift-z` / `Mod-y` | `dispatch(Redo())` |
| `Mod-b` | toggle `Format("bold")` |
| `Mod-i` | toggle `Format("italic")` |
| `Mod-u` | toggle `Format("underline")` |
| `Mod-`\` | toggle `Format("code")` |
| `Mod-k` | toggle `Format("link")` (opens a link prompt; UI is author-supplied) |
| Arrow keys | `dispatch(SetCursor(adjacentRange))` (browser default, intercepted only to dispatch the command) |

Authors override individual keys by spreading `defaultBindings` and replacing keys, or omit the spread to start fresh.

#### 4.3 — Protocol-Layer Escape Hatch

For dynamic bindings (e.g., "Tab inserts a tab in `<code>` but indents a `<list>`"), authors bypass `bindings` and add a `KeyPress` command + `apply` arm:

```ts
const ProseCommandWithKeys = ProseCommand.merge({
    KeyPress: (key: string, modifiers: string[]) => ({ key, modifiers }),
})

const myApply: CommandProtocol<DocumentState, DocumentNode, Union<typeof ProseCommandWithKeys>>["apply"] =
    (state, cmd) =>
        match(cmd, {
            KeyPress: ({ key, modifiers }) => {
                if (key === "Tab" && state.activeBlockKind === "Code") {
                    return defaultApply(state, ProseCommand.Insert("\t", state.cursor))
                }
                // ... dynamic logic
                return Validation.Valid({ next: state, inverse: cmd })
            },
            [__]: (c) => defaultApply(state, c),
        })
```

The renderer fires `KeyPress` for keys not in the `bindings` map, so the two layers compose: `bindings` runs first; unhandled keys flow into `apply` as `KeyPress` commands.

#### 4.4 — Acceptance Criteria

- `defaultBindings` is exported and covers the documented set.
- A `<document bindings={defaultBindings}>` mounts and processes each documented key correctly.
- Spreading and overriding individual keys works (`{ ...defaultBindings, "Mod-b": custom }`).
- Bindings handlers receive the `Dispatcher` only — no separate controller object is constructed or passed.
- Keys not in `bindings` are dispatched as `KeyPress` commands when an extension command for `KeyPress` is registered; otherwise they are silently ignored (browser default behaviour is already prevented by `beforeinput`'s preventDefault).
- A test file `test/ui/prose/bindings.test.ts` covers each documented key, the override path, and the protocol-layer escape hatch.

### 5.0 Out of Scope (Tracked)

#### 5.1 — `parse.text`, `parse.html`, `parse.json`, `documentSchema`

Deferred to v0.4.2. v0.4.1's internal clipboard uses an interim encoder; v0.4.2 lifts it onto `documentSchema` for full round-trip validity.

#### 5.2 — Drag-and-drop, image uploads

Deferred to v0.4.2. v0.4.1 surfaces `paste.files` as the file-handler boundary; drag-and-drop uses the same handler shape.

#### 5.3 — Branching history

Considered during the prose-design grilling and rejected for v0.4.x. Branching is a real feature in some pro tools (Bear, Scrivener) but it's a niche need that complicates the protocol significantly and requires a UI/serialization commitment v0.4.x does not have appetite for. Promote if a real consumer surfaces with a concrete spec.

#### 5.4 — `<remoteSelection>` overlay primitive

Deferred to v0.5.0.

#### 5.5 — Custom-drawn selection (multi-cursor, persistent across blur)

Deferred to v0.5.0.

#### 5.6 — Spell-check / autocorrect overrides

The browser default behaviours pass through. Spell-check is opt-in via `<document spellcheck>`. iOS autocorrect comes through composition events handled by Phase 2. Renderer-level overrides (e.g., disable spell-check inside `<code>` blocks) are deferred until a real consumer asks.

### Design Constraints

- **Additive surface only.** v0.4.1 adds `History.create` + `defaultGrouping`, the `paste` config slot (with `text` + `internal` + `files` defaults; `html` ships in v0.4.2), `defaultBindings` + the `bindings` prop, and three new `ProseCommand` variants (`Undo`, `Redo`, `SetComposing`). Existing surfaces (`ProseRenderer.create`, `<document>`, `parse.jsx`, `proseProtocol`, `Dispatcher`) are unchanged.
- **Schema integration is scoped to where the type fits.** Internal-clipboard JSON goes through `Schema<DocumentState>` (interim Codec in v0.4.1, real `documentSchema` in v0.4.2). The plaintext path is a plain function shared with `parse.text`. HTML paste defers to v0.4.2.
- **History wraps `Dispatcher`.** It returns a `Dispatcher` whose `dispatch` is intercepted; existing `Dispatcher` consumers continue to work unchanged. Authors who do not want history continue to use `Dispatcher` directly.
- **No new external dependencies.** The paste pipeline relies only on browser DOMParser and (for internal-clipboard) `aljabr/schema`. IME relies on browser composition events. History relies on `RefArray` plus the existing `Dispatcher` machinery.
- **All v0.4.0 tests pass without edits.** v0.4.1 features are additive.

---

### Implementation Order

1. Phase 1: History (independent of the others; can ship first as a minimum-viable editor improvement).
2. Phase 4: Default Keyboard Bindings (depends on Phase 1 for `Mod-z` and `Mod-Shift-z`).
3. Phase 2: IME Composition (independent of Phase 1 and 4; can ship in parallel).
4. Phase 3: Paste Sanitization (independent of the others; ships last because the Schema work is the largest single piece).

Phases 1, 2, 3 can pre-release individually for early consumer feedback. Phase 4 is gated on Phase 1.
